# Trio algorithm redesign — implementation plan (revision 2)

Execution-grade plan for implementing the strategy in `reports/Trio algorithm redesign research.md` (the "report") on this fork (`zgoettsc/Trio`, branch `claude/iphone-quick-action-meals-on-zack-copy`, `APP_VERSION = 0.8.3` in `Config.xcconfig`). Evidence for the current state of the code comes from `research_notes/Trio algorithm redesign research/trio_codebase_algorithm.md` (the "audit") and `open_source_aid_innovations.md` (the "OSS note"), re-checked against the working tree where this plan cites a line number. This revision incorporates `reports/Trio algorithm redesign plan review.md` (the "review"); the revision log at the end maps each review finding to the change made. Nothing in the app is changed by this document.

Numbers in this plan are labelled. **[cited]** means the value comes from the report or the research notes (source named). **[initial]** means the value is this plan's starting choice and must be calibrated against the user's own history in S0.4 replay before it is used as a gate; the calibrated value is recorded in the step's pre-registration document.

Findings from re-reading the code that shape the plan:

1. **The dosing core is not replayable as shipped.** `Trio/Resources/javascript/prepare/determine-basal.js` line 5 does `var clock = new Date();`, discarding the `clock` argument of `generate(...)`. On the Swift side the clock is lost at three points: `OpenAPS.determineBasal(currentTemp:shouldSmoothGlucose:clock:...)` (`OpenAPS.swift:410-417`) receives `clock` but the call into the private JS wrapper (`:491-504`) does not pass it, the private `determineBasal(glucose:currentTemp:iob:...)` (`:908-920`) has no `clock` parameter, and `:945` passes `Date()`. `meal()` and `iob()` do receive the clock (`:460-473`). Beyond determine-basal, `trio-oref/lib/determine-basal/autosens.js:27` reads `new Date()` in its non-retrospective path and `prepare/autosens.js` has no clock input, and the profile schedule lookups read the wall clock when a profile is generated (`profile/basal.js:10`, `isf.js:11`, `carbs.js:6`, `targets.js:11`). All schedule lookups use the JavaScriptCore process's local time zone, so a replay on another machine must set the time zone per tick. Fixing these is the first code change (S0.2).
2. **No automated test runs on this fork today.** `.github/workflows/unit_tests.yml` is named `zzz [DO NOT RUN] Automated unit tests` and its job is gated on `if: github.repository_owner == 'nightscout'`. The 123 `@Test` functions across 18 `@Suite` files in `TrioTests/` (Swift Testing; one file, `SettingsExportTests.swift`, imports XCTest; `CoreDataStack.createForTests()`, `TrioTests/CoreDataTests/TestAssembly.swift`) are only run by hand.
3. **Telemetry logs every loop, but outputs only.** `APSManager.logTelemetryLoopSample` (`APSManager.swift:589`, guard at `:591`) gates only on `settings.telemetryEnabled` and writes one `AlgorithmTelemetryLoopSample` per pass (the comment at `:537-539` saying "iff a meal window is active" is stale; the doc comment at `:559-566` says "CONTINUOUSLY" and is correct). The sample carries `bg`, `iob`, `cob`, `eventualBG`, `minPredBG`, `insulinReq`, `smbDelivered`, `tempBasalRate`, `reason`, Kalman `velocity`/`acceleration` (`AlgorithmTelemetryEvent.swift:56+`) but none of the 13 JSON inputs. Local telemetry is purged after 30 days (`AlgorithmTelemetryManager.swift:1046-1048`).
4. **The Kalman filter is fed wrongly today.** `APSManager.swift:507-520` calls `signalPipeline.processGlucose(rawBG: determination.bg, at: now, ...)` once per loop (3-minute cadence, `Config.loopInterval`) stamped with loop time, not CGM reading time; `OrefSignalPipeline.swift:150-158` has no de-duplication; `AdaptiveKalmanFilter.reset()` (`:113`) and `BGSignalProcessor.history` are in-memory, so every relaunch starts unconverged. The two committed exports (`docs/signal_export_7d_2026-04-16.json`, `docs/meal_export_7d_2026-05-14.json`) were produced by this feed and cannot serve as a correctness reference. The feed is fixed in Stage 0 (S0.8) before any Kalman output touches dosing.
5. **Plugin CGMs supply no quality fields.** `Trio/Sources/APS/CGM/PluginSource.swift:245-252` hard-codes `noise: nil, type: "sgv"` for every plugin CGM (G5/G6/G7/Libre), and nothing in the tree stores a `"cal"` record; only the Nightscout/xDrip JSON path can carry `noise`. Any safety relaxation must therefore rest on positive evidence computed from the glucose series itself, never on the absence of a flag.
6. **The repository is public.** `gh api repos/zgoettsc/Trio` returns `private: false, visibility: public`, and a `telemetry` branch exists on it. `TrioSettings.telemetryRepo` defaults to `"zgoettsc/trio"`, `telemetryBranch` to `"telemetry"` (`TrioSettings.swift:259-260`). Whatever has already been pushed there is health data in public. This is addressed before anything else (S0.0).

## 0. Decision points to resolve before Step 1

### 0(a) Rebase onto upstream Trio v1.0.x Swift oref, stay on JS, or hybrid

**Recommendation: hybrid now, rebase as a Stage 0 workstream verified by the harness rather than a prerequisite for it.** Every new layer (harness, supervisor, sizing, estimator, learner) is written in Swift against a `DosingCore` protocol with two implementations, `JSOrefCore` (wraps today's `JavaScriptWorker` + bundle) and, once the rebase lands, `SwiftOrefCore` (wraps upstream's Swift oref). No new dosing logic goes into `trio-oref/lib/*.js`. The JS edits in the whole plan are the determinism edits listed in S0.2 (clock in `prepare/determine-basal.js`; an explicit `now` plus `retrospective: true` in `prepare/autosens.js`; an optional `now` argument in `prepare/profile.js`, or profile generation moved to Swift for replay). The fork's multiplicative meal-window stack is retired by starving its inputs from Swift (forcing `mealWindowActive`/`toughMealActive` false and `mealWindowAutoPhantomCOBLevel` 0 in `TrioCustomOrefVariables`), not by editing JS; all six fork hunks key on those variables (`determine-basal.js:136-142, 191-234, 868-882, 981-983, 1626-1684, 1736-1822`).

Why not "rebase first":

- **Cost.** `MERGE_NOTES.md` documents an unfinished sync to v0.8.3 only: `project.pbxproj` taken from upstream and ~40 fork files re-added by hand across 12 groups, three Swift conflicts, submodule cleanup, deleted `Models/Autotune.swift`/`SavitzkyGolayFilter.swift`. Reaching v1.0.2 adds: the JS plumbing in `OpenAPS.swift` is gone upstream; the 306 fork JS lines must be re-expressed or dropped (they are dropped, S1.2); the `TrioCustomOrefVariables` seam may be reshaped (Tai PR #19 shows `DetermineBasalGenerator.swift` with an `autoISFStatus` argument). Upstream v1.0.2 Swift sources were not readable from this environment (OSS note Q4 "Gaps"), so S0.5 begins with a time-boxed 2-day spike reading them before any estimate is committed to; the working estimate is 12–20 developer-days plus 3–5 days of differential verification, unverified.
- **Fidelity risk.** Upstream states "the decisions themselves have not changed" without a published differential test; known divergences are issue #1359 (sub-30-minute zero-temp emulation uses an inverted low-temp rate formula) and #1610 (dynamic ISF silently disabled under late G7 readings). The harness turns the rebase into a measured equivalence test (S0.5 gate).
- **Cost of staying on JS.** Zero now; every JS edit ported twice later; stranded on 0.8.3. Acceptable for 3–6 months. (The `weightPercentage` 0.35/0.65 mismatch cited in the audit is cosmetic: the JS reads `profile.weightPercentage` only in a `< 1` test and in log strings, `determine-basal.js:300, 390-392, 677`; the actual weighting is Swift's 0.35 at `OpenAPS.swift:574-587`.)
- **Cost of the hybrid.** `DosingCore` + `JSOrefCore` ≈ 3 days; `SwiftOrefCore` ≈ 3 days later. `OpenAPS` is constructed directly at `APSManager.swift:155` with a private `jsWorker` (`OpenAPS.swift:7`), so the core is injected through `OpenAPS.init(storage:tddStorage:core:)`, a signature change, not a DI registration.

### 0(b) Where the replay harness runs, and how the same code runs everywhere

**Recommendation: one local Swift package, `AlgorithmKit/` (`Package.swift`, platforms iOS 17 and macOS 14), consumed by the app as a local SPM dependency and tested on macOS with `swift test`.** Contents: `DosingCore` and `JSOrefCore`, all pure value-type algorithm modules, the replay engine, metrics, scenario/trace formats, and a `trio-replay` executable. No Core Data, Swinject, UIKit or `FileStorage` inside the package.

Guarantees:

- Single source: the app links the package. App-side adapter files (`DosingTraceStore`, `DosingPipelineAdapter`, `MealWindowStore`, export view, model v2) each require a `project.pbxproj` edit because `Trio/Sources` is not a synchronized group (only `Preview Content` and `Views` are `PBXFileSystemSynchronizedRootGroup`s); to contain this and keep the rebase conflict in `MERGE_NOTES.md` section A small, all new app-side files live under one new synchronized group `Trio/Sources/APS/AlgorithmLab/`.
- The JS bundle is a package resource; `Trio/Resources/javascript/bundle/` becomes a symlink to it, and `scripts/check-bundle-parity.sh` fails CI when SHA-256s differ.
- Every loop trace and replay report records `algorithmFingerprint = {gitSHA (full 40-char, from the package's build step; BuildDetails.plist only carries a 7-char abbreviation, scripts/capture-build-details.sh:25), packageSHA, bundleSHA256s, coreName, timeZoneIdentifier}`.
- Determinism: the clock and time-zone fixes in S0.2; `DosingCore.run(inputs:clock:timeZone:)` is a pure function of its arguments by contract; `trio_custom_oref_variables` is an *input document* captured per loop and never recomputed inside the core (so the five `Date()` calls in `prepareTrioCustomOrefVariables`, `OpenAPS.swift:562-641`, do not affect purity).
- CI reality: `JSOrefCore` needs JavaScriptCore, which exists only on Apple platforms, so package tests run on GitHub-hosted macOS runners (6-hour job cap, 10× minute multiplier). The per-PR job is kept under 15 minutes (unit tests + `verify` on a 3-day fixture + a 3-subject × 1-day in-silico smoke). The nightly 90-day replay and the full in-silico set run on the developer's Mac via `launchd` (`tools/nightly.sh`), uploading reports to the private location in 0(d). A Node runner of the identical bundle for Linux CI is an optional later addition, gated by a JSC-vs-Node parity test.

Python is used only for simulation and notebook analysis; it drives `trio-replay tick` as a subprocess (the `LoopAlgorithmRunner` precedent, OSS note Q3).

### 0(c) In-silico simulator and wiring

**Recommendation: simglucose (UVA/Padova 2008 cohort, 30 virtual subjects, Python) as the screening cohort; a personal twin fitted to the user's own data as *secondary* evidence only.** S0.7 starts with a one-day feasibility spike that records measured facts before any gate is fixed: which simglucose release is installable and whether the 2026 counter-regulation/activity extension exists as code; whether PyReplayBG is usable or a reduced twin (minimal-model glucose, two-compartment subcutaneous insulin, two-compartment gut) must be fitted locally; the measured per-tick runtime of `trio-replay tick`; and baseline oref's TIR on the cohort.

Identifiability limitation (stated up front): without a meal record, meal size and insulin sensitivity are not jointly identifiable from CGM + insulin alone; a twin fitted on episodes whose "grams" were inferred with the profile ISF/CR is circular. The twin is therefore fitted on held-out insulin-response windows only (fasting nights; isolated corrections where they exist), its profile-likelihood identifiability for insulin sensitivity and meal gain is reported, and its counterfactuals are used as consistency checks (does the direction of the effect agree with divergence scoring?) never as a promotion criterion on their own. A 30-/60-minute RMSE is reported against a persistence baseline, not as an absolute gate (a persistence forecast meets 25 mg/dL at 30 minutes on most days).

Wiring: `tools/insilico/TrioController` adapter; per 5-minute step writes `tick.json`, calls `trio-replay tick --core js --stages <config> --tz <id>`, applies `rate`/`units`; fixed seeds; scenario files for meals (time, grams, absorption class), exercise, missed doses, sensor dropouts, compression artefacts. In-silico false-positive rates understate real ones (report item 6: 0.05/day in silico vs 0.17 on OhioT1DM), so simulation screens for gross failures and the user's own data decides promotion.

### 0(d) Freezing the baseline, and where the data lives

**Recommendation: tag the installed build's commit, snapshot its settings, hash the bundle, and keep all history data out of the public repository.**

- Code: read the 7-char SHA from the installed app's `BuildDetails.plist`, resolve it to the full commit, `git tag baseline-live-2026-10`. Record SHA-256 of each `Trio/Resources/javascript/bundle/*.js` at that commit.
- Settings: existing Settings Export module (`Trio/Sources/Modules/SettingsExport/SettingsExportProvider.swift`) plus copies of `preferences.json`, `settings/profile.json`, `settings/pumpprofile.json`, `settings/basal_profile.json`, `settings/insulin_sensitivities.json`, `settings/carb_ratios.json`, `settings/bg_targets.json`, `freeaps/freeaps_settings.json`, `settings/therapy_profiles.json` (`Trio/Sources/APS/OpenAPS/Constants.swift:29-42, 94, 97`), including the meal-window knobs in `TrioSettings.swift:83-129, 205-222`. Settings contain no glucose data and may be committed with a SHA manifest.
- Data: the 90-day history export (S0.3) is **never committed to the repository**. It lives in `~/TrioLab/fixtures/` on the developer's Mac and in an encrypted archive (age/gpg) in private cloud storage, referenced from the repo only by SHA-256 in `AlgorithmKit/Fixtures/MANIFEST.json`. Fixture file names carry no dates that identify the person.

Because S0.3 changes the Core Data model, the baseline tag gets a companion `baseline-live-2026-10-cd2` (the baseline code with only the v2 model cherry-picked) so a baseline build remains installable after migration; see S0.3.

## 1. Workstreams and ordered steps

Conventions used in every step:

- **Stage modes.** Every new dosing component is a `DosingStage` with a persisted `mode: DosingStageMode` ∈ {`off`, `shadow`, `reduceOnly`, `live`}, default `off`. `shadow` computes and logs; `reduceOnly` applies only reductions of insulin relative to the core proposal; `live` applies everything. Modes live in `AlgorithmLabSettings` nested in `TrioSettings` (decoded with `try?` + defaults like the rest of `TrioSettings.swift:311+`, so a missing key cannot flip a stage on). Where a stage's `reduceOnly` would have no effect, the step says so and the rollout goes shadow → live with reduced parameters instead.
- **Kill switch.** `algorithmLab.killSwitch: Bool` (default `false`). When true the pipeline runs exactly two things: the supervisor in `live` if the supervisor has ever been promoted to live (`algorithmLab.supervisorPromotedAt != nil`), otherwise nothing; and the legacy stack in `retired`. Every other stage is treated as `off` regardless of its stored mode, all derived profile/preference overrides are removed, and the trace marks `killSwitch: true`. The landing state is therefore always "core only + supervisor" (or "core only" before the supervisor was ever promoted), never "whatever modes were set". The legacy stack toggle is `legacyStack: enabled | retired` (default `enabled` until S1.2 flips it) so that the safe state is spelled `retired` everywhere and no toggle has inverted semantics.
- **Fail-safe.** `DosingPipeline.apply` is wrapped: any thrown error or precondition failure inside a stage returns the unmodified core determination, increments `pipeline.exceptionCount`, and writes a trace row with the stage name and error. Swift traps are avoided by construction (no force-unwraps or array indexing without bounds checks in package code; `swiftlint` rule set in the package). A test injects a throwing stage and asserts the core proposal passes through; a second test injects a stage that returns `units > unitsCore` in `reduceOnly` and asserts it is clamped. Pipeline exceptions feed stop condition 10.
- **Hook point.** `DosingPipeline` runs inside `OpenAPS.determineBasal` immediately after `determination.timestamp = deliverAt` (`OpenAPS.swift:517`) and before `await processDetermination(determination)` (`:540`), so the stored `OrefDetermination` that `APSManager.enactDetermination` reads (`APSManager.swift:1682-1714`) is the post-pipeline decision. Derived per-loop **profile** overrides (the PR #1506 pattern) are applied to the `profile` JSON document loaded at `:425` before it is passed to the core; the only key the JS reads from `preferences` are `useNewFormula`, `sigmoid`, `adjustmentFactor`, `adjustmentFactorSigmoid`, `curve`, `useCustomPeakTime` (grep of `preferences.` in `determine-basal.js`), so everything else (`maxDelta_bg_threshold`, `min_bg`/`max_bg`/`target_bg`, `sens`, `threshold_setting`) is patched in the profile document, never in `preferences`.
- **Threshold pin.** Whenever any derived override lowers the profile target, the pipeline sets `profile.threshold_setting` to the threshold the core would have computed from the un-overridden target (`threshold = min_bg − 0.5 × (min_bg − 40)`, then `min(max(threshold_setting, threshold, 60), 120)`, `determine-basal.js:733-737`), so the core's LGS/SMB-disable floor and the supervisor's hard floor do not move with the override.
- **TDD anchor.** Every cap and budget uses `TDD10d` = the 10-day average of `TDDStored.total` (`average_total_data` as computed at `OpenAPS.swift:574-587`, or a 7-day average when fewer than 10 days exist), never `weightedAverage`, which contains the 2-hour extrapolation (`0.35 × avg(last 2 h rows) + 0.65 × avg(10 d)`) and inflates during the very SMB trains the caps exist to bound. Both values are logged.
- **Trace.** Every stage appends `DosingStageTrace {stage, mode, proposalIn, proposalOut, reasons[], numbers{}}` to the loop's `DosingTrace` (S0.3). "Telemetry fields" below are keys in `numbers`.
- **Safety co-primaries and margins** (§4 has the statistics). Efficacy endpoints are judged by 90% block-bootstrap CIs. Safety is judged two ways at once: (i) event-count stop rules that halt the arm immediately (any <54 mg/dL episode ≥15 minutes attributable to a non-baseline stage; <70 episodes per week exceeding the baseline weekly mean + 1 for two consecutive weeks; any <70 episode within 2 hours of a decision where the candidate delivered more insulin than the core proposed); (ii) pre-registered non-inferiority margins evaluated at the end of the arm with 28 paired days per arm minimum: TBR <70 **+1.0 pp**, TBR <54 **+0.3 pp**, LBGI **+0.5**, max rolling-60-minute SMB total ≤ baseline 99th percentile, IOB never above `max_iob`, insulin/day within ±10% of baseline unless the step intends otherwise [all initial; the power statement in §4 explains why 28 days and these widths]. The previous revision's +0.3/+0.1/+0.2 margins are withdrawn as unachievable at n-of-1 scale.
- **Shadow duration**: ≥4 weeks and ≥20 labelled episodes [cited: report, Environment 4] unless stated; each live sub-step held 2 weeks; only the stage under test may change during an arm (any other app change ends the arm and the fingerprint-drift stop condition is what enforces it).
- **Review checkpoints.** A named second person (endocrinologist or experienced looper; recorded in `docs/experiments/REVIEWER.md`) signs off before: the first add-insulin path goes live (S1.3 `reduceOnly → live`), S2.1 `shadow → live`, S2.5 `reduceOnly → live`, and any third iteration of a step. The reviewer also blind-labels 15 of the 30 calibration episodes (§2.5).
- **Shadow modules referenced**: `AdaptiveKalmanFilter`, `BGSignalProcessor`, `BGResidualCalculator`, `MacroMealModel`, `ExerciseSensitivityModel`, `DailyStateVector`, `GarminZScoreNormalizer`, `AdaptiveLearning`, `SignalStore`, `OrefSignalPipeline` (all `Trio/Sources/APS/SignalProcessing/`), `MealClassifier`, `PumpSiteAge`, `SmartSenseManager`.
- **Availability assumption.** Effort is developer-days for one developer. The week table in §6 assumes full-time; at 50% availability every calendar milestone roughly doubles (Stage 1 live at month 6, not 3).

### 2.2 Deterministic replay engine

`ReplayEngine.run(history:core:pipeline:from:to:mode:)`. One tick per stored loop time (reproducing 3-minute cadence and skipped loops). `.faithful` replays stored inputs byte-for-byte (`verify`); `.reconstructed` rebuilds inputs from entities for the same tick times (backfilled period; validates the reconstructor). Reconstruction per tick: glucose = 72 most recent rows at or before the tick with smoothing applied per the settings snapshot and manual readings raw (`OpenAPS.swift:160-170`); pump history = 24 h with the orphaned-resume filter as of the tick; `currentTemp` from the last temp event minus elapsed minutes (`APSManager.swift:1643-1668` fallback; ±1 min tolerance); carbs 24 h excluding rescue; profile = per-loop determination fields (backfill) or trace snapshot; autosens re-run when the stored one is >30 min old at the tick; TDD from `TDDStored`; overrides/temp targets active at the tick; `monitor/iob.json` regenerated by the core's `iob` entry point and compared to stored; time zone set per tick from the trace (or, for backfill, from the device's time-zone history if recorded, else the current zone flagged `tzProvenance: "assumed"`).

**Counterfactual approximation.** Two methods, never pooled: (1) **decision-divergence scoring** (default, Environment 3): each tick scored on stored inputs; divergence per tick (Δunits, Δrate) contextualised by what happened next at +30/+60/+120 min, any <70 within **6 hours** (not 2: the slow-meal tail is the failure mode of interest), any >250 within 2 hours; the candidate's IOB is propagated through its own decisions so budgets/ceilings use candidate IOB; reported in both directions ("dosed more into a later low", "dosed less into a confirmed rise", "insulin in hours 3–6 after onset vs baseline"); (2) **twin resimulation** (Environment 2, secondary): counterfactual glucose from the candidate's deliveries with the twin's fit quality and identifiability caveats attached (0(c)); used as a direction/consistency check.

## 3. Safety supervisor specification

The supervisor is unconditionally first because every other change adds insulin somewhere, and the only mechanism that bounds all of them at once is a layer that runs last, sees the final proposal, and can only subtract. It also makes the kill switch meaningful: its landing state "core + supervisor" is strictly safer than baseline.

**Form.** The supervisor computes, for each rule *i*, a candidate `(units_i, rate_i)`, and outputs `units' = min(unitsIn, min_i units_i)` and `rate' = min(rateIn, min_i rate_i)`; `duration' = max(durationIn, 30)` only when `rate' = 0`. Nothing else is permitted by the type: the output constructor takes `(in, candidates)` and clamps. Rules that "resume" or "fall back" act only on suspensions the supervisor itself imposed (tracked by `sup.suspendOwner`); they can never lift a core zero temp or raise a core low temp. Supervisor state (`monitor/supervisor-state.json`: suspend owner and start, hysteresis counters, rolling budget ledger, anti-windup counters, under-delivery timer) is the source of truth, written before enactment every loop and restored on relaunch; memory is a cache.

3.1 **CGM quality gate.** Quality is classified from the series itself because plugin CGMs supply no `noise` (`PluginSource.swift:245-252`): `stale` (newest ≥12 min or clock skew < −5 min) → `units_1 = 0`, `rate_1 = basal` (i.e., `rate' = min(rateIn, basal)`); `suspect` (any of: single-step discontinuity >20% of bg between consecutive readings; raw-vs-Kalman innovation >15 mg/dL [initial]; reversal >15 mg/dL within 10 min; `bg ≤ 38`; `noise ≥ 3` when the field exists; new sensor session <2 h when `sessionStart` exists) → `units_1 = 0`; `ok` requires positive evidence (≥3 consecutive readings with consistent deltas, Kalman converged, innovation within bounds); `unknown` (insufficient readings to judge) → no reduction and **no relaxation anywhere in the pipeline**. Noise-2 halving, calibration-record rules and "no calibration in 30 min" preconditions are removed from this plan until a CGM path supplies those fields; if the user's CGM path ever does (Nightscout/xDrip), they are added back as a separate step with their own tests.

3.2 **30-minute predictive suspend.** `predBG30 = bg + 30 v` with Kalman `v` when converged and fresh, else finite-difference slope over the last 3 raw readings [cited: report item 2 for the 80 mg/dL line]. If `bg < 70` or `predBG30 < 80`: `units_2 = 0`, `rate_2 = 0`, `duration ≥ 30`; owner = supervisor unless the core already proposed 0 (owner = core). Hysteresis applies to supervisor-owned suspends only: hold until `predBG30 ≥ 90` and `v ≥ 0` on two consecutive ticks [initial]. **Resume after prolonged suspend:** when the supervisor has owned a continuous zero temp for 150 minutes [initial; oref's own LGS caps a single zero temp at 120 min, `determine-basal.js:1427`], the supervisor's own candidate becomes `rate_2 = 0.5 × basal` for 30 minutes unless `bg < 70`; because the output is `min(rateIn, …)`, this only ever lets the *core's* proposal through, never raises it. A carbs-required notification uses the existing `carbsReq` path.

3.3 **Velocity gate.** `g(v) = 1` for `v ≥ 0`, `0` for `v ≤ −1 mg/dL/min` [cited: zone-MPC], linear between. `units_3 = unitsIn × g(v)`; `rate_3 = basal + max(0, rateIn − basal) × g(v)`, so a low temp is never raised toward basal (basal 1.0, core 0.3, v −0.5 → 0.3). Deceleration brake: `a < −0.05 mg/dL/min²` [initial] and `bg < 180` → `units_3 ×= 0.5`.

3.4 **IOB ceiling.** `units_4 = max(0, iobCeilingPercent × maxIOB − iob − unseen)` with `iobCeilingPercent 90` [initial; autoISF `iobTHvirtual` lineage] and `unseen` from 3.7; temps may fill to 100% (`determine-basal.js:1687-1691`).

3.5 **Rolling budgets.** Rolling-60-minute automated insulin ≤ `max(1.0 U, 8% × TDD10d)`; rolling-180-minute ≤ `15% × TDD10d`; per detected episode (S2.1; before that per 6-hour window) ≤ `20% × TDD10d` [all initial; calibrated so <2% of baseline SMB volume on non-episode days is clipped]. **Data source:** proposals are counted into the ledger immediately at the loop that emits them; the ledger reconciles against pump history (`BolusStored`/`TempBasalStored`) and against `enacted.pumpSuspended` (enactment is skipped when the pump is suspended, `APSManager.swift:1694-1698`); an unreconciled proposal counts as delivered for 30 minutes [initial], then is dropped if pump history never shows it. Omnipod reports a bolus on completion, so the ledger, not pump history, is authoritative for the first minutes.

3.6 **Anti-windup.** Max temp (`rate ≥ maxSafeBasal`) or SMB at cap for 420 continuous minutes [cited: 780G 7 h] → `rate_6 = basal`, `units_6 = 0` for 60 minutes, and a notification ("insulin not working as expected; check site"); zero temp cumulative ≥180 minutes in 6 hours [initial] → notification plus the 3.2 resume rule for supervisor-owned suspends. Both are subtract-only candidates; neither can raise anything.

3.7 **Insulin onset accounting.** Automated insulin delivered within the onset time (`rapid-acting` 20 min, `ultra-rapid` 12 min, custom `insulinPeakTime/4` [initial]) is counted at 100% as `unseen` for 3.4 and 3.5.

3.8 **Hard floor and ceiling (`supervisorHardFloorEnabled`, default true, immune to `killSwitch`).** `units_8 = 0` if `bg < threshold` (the core's stored `threshold`, pinned during overrides); `units_8 ≤ min(3.0 U [cited: iLet], 0.05 × TDD10d)` (TDD 40 → 2.0 U).

3.9 **Under-delivery / site-failure detector (flag, not a dose change).** Glucose >250 for ≥3 h with IOB rising and glucose not falling ≥10 mg/dL over the last hour [initial] → `sup.underDeliverySuspect = true`, a site-check notification, and the positive effects of S2.2/S2.3 are suppressed while the flag holds; the supervisor itself does not reduce insulin for this flag (a failing site needs more insulin from a new site, not less from the loop), and the anti-windup notification is the user-facing path. Stop condition 13 covers the ≥4 h case.

**Failure modes outside the supervisor's view and their handling:** pump suspended (ledger reconciliation, 3.5, and `enacted.pumpSuspended` on the dashboard); duplicated/delayed Omnipod history (ledger-first counting, reconciliation window); phone reboot mid-loop (state file authoritative; Kalman re-seeded from `GlucoseStored` by S0.8); app crash loops (pipeline fail-safe; loop-failure stop condition; the 3 a.m. runbook).

Tests are listed in S1.1; the property test over random proposals including low temps and core zero temps, and the shadow trace assertion, are the invariant.

## 4. Measurement and decision framework

- **Baseline period.** 28 days of recording with the frozen baseline before any live change, plus the backfilled history for replay.
- **Arm length and power.** Safety co-primaries are evaluated two ways (conventions). For the CI-based non-inferiority check: with day-level paired differences and a daily TBR <70 SD of 2–4 pp (to be measured on the user's baseline; the plan assumes 3 pp), a 90% block-bootstrap CI on 14 paired days has half-width ≈1.3 pp and on 28 paired days ≈0.9 pp. Margins of +1.0 pp (TBR <70), +0.3 pp (TBR <54), +0.5 (LBGI) are therefore pre-registered with **28 paired days per arm minimum** (two 28-day cycles per step), and the pre-registration states the measured SD and the resulting power (≥80% to declare non-inferiority when the true difference is ≤0). TBR <54 is too rare for a CI at this scale; it is governed by the event-count rule (any attributable episode halts the arm). The event-count rules act immediately, every day, independent of the CI.
- **Design.** Reversible fast-acting changes: ABAB alternating-week crossover over two 28-day cycles, 24-hour washout after each switch; A is the exact previous promoted state, recorded by fingerprint; learned libraries and calibrated budgets are frozen per cycle (S2.3 v2 is evaluated only after its library is frozen). Learner: interrupted time series with a 4-week pre-period plus walk-forward replay as primary evidence. Pre-registration per step in `docs/experiments/<step>.md` before the toggle flips: primary endpoint, co-primaries and margins, arm length with the power statement, analysis, rollback, reviewer name where required. Iterations are capped at two per step; a third requires reviewer sign-off or reversion. Only the stage under test may change during an arm.
- **Confounders.** Site changes: exclude the first 6 h after a pod change from episode metrics; stratify by site-age band. Illness/stress: a one-tap "sick day" flag (a one-time manual input, acceptable under the constraint) excludes the day from both arms. Travel: time-zone change from the per-loop `timeZoneIdentifier` excludes ±1 day. New sensor: first 12 h excluded from detector metrics. Exercise: a stratum, never excluded. Therapy-profile switches and settings edits end the arm.
- **What counts as a win.** Primary endpoint improves with the 90% CI lower bound above the pre-registered minimum (AUC −10%, TAR −3 pp, TIR +3 pp, time-to-first-adequate-correction −10 min), no event rule tripped, every CI-based safety margin held. Win on primary with a margin breach = iterate (tighten the step's parameters, re-shadow 2 weeks, max two). Neither win nor loss after two cycles = revert.
- **Standing dashboard** (`trio-replay dashboard` nightly; `AlgorithmLab` screen in the app): TIR/TITR/TBR<70/TBR<54 (night/day)/TAR>180/TAR>250, mean/SD/CV, LBGI/HBGI (7- and 28-day, by arm); postprandial peak and AUC per labelled episode; time-to-first-adequate-correction; insulin in the first 60 min and hours 3–6 after onset; insulin/day and automated fraction; SMB count, stacking, IOB max; suspensions by owner, false suspends, rebound highs; supervisor clip counts by rule; budget ledger reconciliation gaps; detector sensitivity/delay/outcome-FP per day with tap/no-tap split; learner per-block values vs corridor, posterior widths, "not identifiable" blocks; CGM quality distribution (`ok|suspect|unknown|stale`); Kalman-vs-finite-difference disagreement alerts and `updatesSinceReset`; fingerprint drift; loop duration p95; loop/enactment failure rate; pipeline exception count; under-delivery flags; pump-suspended loops.

**Stop conditions (halt the program, land on "core + supervisor", write an incident note before anything else):**
1. Any glucose <54 mg/dL for ≥15 minutes, or any event needing assistance, within 6 hours of a decision where the candidate delivered more insulin than the core proposed.
2. Two nights in any 7 days with a <70 event the trace attributes to a non-baseline stage.
3. A supervisor trace with `unitsOut > unitsIn` or `rateOut > rateIn`, even once.
4. Fingerprint drift during a live arm.
5. `verify` below 99% for 3 consecutive days, **or any `verify` mismatch on a loop where insulin was delivered**.
6. Detector outcome-FP >1.0/day for 7 days, or any FP ending below 60 mg/dL.
7. Learner value outside its corridor, or the same-hour low on 2 nights after a learned change.
8. Occlusion/pod-fault rate >1 per week above baseline after any change that increases per-SMB size.
9. Dual-hormone: any unconfirmed enactment, budget breach, or sign of increased insulin aggression because glucagon exists.
10. Pipeline exceptions on >0.5% of loops in a day, any app crash loop (≥3 crashes in an hour), or loop-failure rate (`LoopStatRecord.loopStatus != "Success"`) more than double the baseline week for 2 days.
11. Supervisor state file unreadable or failing its checksum (the supervisor then runs stateless with budgets at zero until repaired, which is itself a halt of all add-insulin stages).
12. Any health data found in a public location (repo, branch, report upload).
13. Under-delivery: glucose >250 for ≥4 hours with IOB rising and no fall, on any day a non-baseline stage was live (investigate site and stage; stage off until explained).

### 6.2 The 3 a.m. runbook (`docs/RUNBOOK.md`, one page, tested once in daylight)

1. **Stop automated insulin now:** Settings → Closed Loop off (`closedLoop = false`; `executeLoop` then skips `enactDetermination`, `APSManager.swift:327-345`); or suspend the pump from the pump screen; or remove the pod. Treat the low per the user's own plan first.
2. **Kill switch:** Settings → Algorithm Lab → Kill switch. Effect: core + supervisor (if ever promoted) only; all other stages off; all derived overrides removed; legacy stack retired. It does **not** open the loop and does **not** cancel a running temp or an in-progress bolus (cancel those on the pump screen).
3. **Confirm what the loop is doing:** the next determination's `reason` ends with `[lab: killSwitch]`; the Algorithm Lab screen shows `pipeline: identity` and `supervisor: live|off`.
4. **Preserve evidence:** export `dosing-trace` (share sheet) before deleting anything; traces are at `Documents/dosing-trace/`, supervisor state at `monitor/supervisor-state.json`, logs via the existing debug export.
5. **Morning:** run `trio-replay verify --days 1` on the exported trace; file the incident note; do not re-enable any stage until the note names the cause.
6. **Who to call:** the named reviewer; the user's clinical contact.
