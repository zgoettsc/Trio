# Trio algorithm redesign — implementation plan

Execution-grade plan for implementing the strategy in `reports/Trio algorithm redesign research.md` (the "report") on this fork (`zgoettsc/Trio`, branch `claude/iphone-quick-action-meals-on-zack-copy`, working tree at commit `b38a5a418f8678b9799045b4019b7c921990bce0`, `APP_VERSION = 0.8.3` in `Config.xcconfig`). Evidence for the current state of the code comes from `research_notes/Trio algorithm redesign research/trio_codebase_algorithm.md` (the "audit") and `open_source_aid_innovations.md` (the "OSS note"), re-checked against the working tree where this plan cites a line number. Nothing in the app is changed by this document.

Three findings from re-reading the code shape everything below and are not in the audit:

1. **The dosing core is not replayable as shipped.** `Trio/Resources/javascript/prepare/determine-basal.js` line 5 does `var clock = new Date();`, discarding the `clock` argument, and `Trio/Sources/APS/OpenAPS/OpenAPS.swift:945` passes `Date()` rather than the `clock` parameter that `OpenAPS.determineBasal(currentTemp:shouldSmoothGlucose:clock:)` receives (`OpenAPS.swift:413`). `meal()` and `iob()` do receive the clock. Until this is fixed, re-running a stored loop produces a different `deliverAt`, different `lastBolusAge`, and different staleness decisions. This is the first code change in the plan.
2. **No automated test runs on this fork today.** `.github/workflows/unit_tests.yml` is named `zzz [DO NOT RUN] Automated unit tests` and its job is gated on `if: github.repository_owner == 'nightscout'`. The 99 test functions in `TrioTests/` (Swift Testing, `@Suite`/`@Test`, `CoreDataStack.createForTests()`, `TrioTests/CoreDataTests/TestAssembly.swift`) are only run by hand. CI integration is therefore a build task, not a configuration task.
3. **The telemetry stream already logs every loop, but not the inputs.** `APSManager.logTelemetryLoopSample` (`APSManager.swift:560-800`) gates only on `settings.telemetryEnabled` and writes one `AlgorithmTelemetryLoopSample` per pass to `loop.jsonl` (the comment at `:546` saying "iff a meal window is active" is stale; the function body has no window gate). The sample carries outputs (`bg`, `iob`, `cob`, `eventualBG`, `minPredBG`, `insulinReq`, `smbDelivered`, `tempBasalRate`, `reason`, Kalman `velocity`/`acceleration`) but not the 13 JSON inputs, so it supports scoring but not re-execution. The two 7-day exports in `docs/` (`signal_export_7d_2026-04-16.json`, 2,016 Kalman rows; `meal_export_7d_2026-05-14.json`, 20 meal records with `loopDecisions`, `bolusEvents`, `tempBasalEvents`, BG traces) have the same limitation.

## 0. Decision points to resolve before Step 1

### 0(a) Rebase onto upstream Trio v1.0.x Swift oref, stay on JS, or hybrid

**Recommendation: hybrid now, rebase as a Stage 0 workstream that is verified by the harness rather than a prerequisite for it.** Concretely: every new layer (harness, supervisor, sizing, estimator, learner) is written in Swift against a `DosingCore` protocol with two implementations, `JSOrefCore` (wraps today's `JavaScriptWorker` + bundle) and, once the rebase lands, `SwiftOrefCore` (wraps upstream's Swift oref). No new dosing logic goes into `trio-oref/lib/*.js`; the only JS edit in the whole plan is the five-line clock fix. The fork's multiplicative meal-window stack is retired by starving its inputs from Swift (forcing `mealWindowActive`/`toughMealActive` false in `TrioCustomOrefVariables`), not by editing JS.

Why not "rebase first" as the report's Stage 0 phrases it:

- **Cost of the rebase.** `MERGE_NOTES.md` documents an unfinished sync to v0.8.3 only: `project.pbxproj` must be taken from upstream and ~40 fork files re-added by hand across 12 groups (`Modules/AIInsightsConfig/` 11 files, `Services/SmartSense/`, `Services/Garmin/`, `Services/ProfileManager/` + therapy-profile modules, `Modules/PhysioTesting/` + storage, `APS/SignalProcessing/` 10 files, `Services/HealthKit/`, `Models/Weekday.swift`), three Swift conflicts (`TrioSettings.swift`, `TreatmentsStateModel.swift`, `TreatmentsRootView.swift`), submodule cleanup, and the deleted `Models/Autotune.swift`/`SavitzkyGolayFilter.swift`. Reaching v1.0.2 (7 Oct 2026, OSS note Q4) adds: the entire JS plumbing in `OpenAPS.swift` (`JavaScriptWorker`, `Prepare`/`Bundle` constants, `middleware`) is gone upstream; the 306 lines of fork JS (`determine-basal.js` hunks at 136-234, 268-298, 868-882, 981-983, 1626-1684, 1736-1822) must either be re-expressed in Swift oref or dropped; `TrioCustomOrefVariables` → `trio_custom_oref_variables.json` may have been reshaped (Tai's PR #19 shows the Swift entry point is `DetermineBasalGenerator.swift` with an added `autoISFStatus` argument). Estimate: 12–20 developer-days for a solo developer who also has to re-verify Garmin/SmartSense/HealthKit wiring, plus 3–5 days of differential verification. The upstream Swift sources were not readable from this environment (OSS note Q4 "Gaps"), so the seam-compatibility part of that estimate is unverified.
- **Fidelity risk of the Swift core.** Upstream states "the decisions themselves have not changed" without publishing a differential test. Known divergences: issue #1359 (sub-30-minute zero-temp emulation uses an inverted low-temp rate formula in `oref-swift`), issue #1610 (dynamic ISF silently disabled when G7 readings arrive late). The fork cannot detect such divergences today because it has no replay. Building the harness first turns the rebase from a bet into a measured equivalence test (gate in S0.5: ≥99.5% identical `rate`/`duration`/`units` over 90 replayed days, every mismatch explained).
- **Cost of staying on JS.** Zero port cost now, but every JS edit is ported twice (report, "Trio today" section), the fork is stranded on 0.8.3 without upstream's CGM-plugin and dosing-mode work, and the `weightPercentage` 0.35/0.65 mismatch (`Preferences.swift:50` vs `trio-oref/lib/profile/index.js:77`) persists. Acceptable for 3–6 months, not indefinitely.
- **Cost of the hybrid.** `DosingCore` protocol + `JSOrefCore` adapter ≈ 3 days; `SwiftOrefCore` adapter ≈ 3 days later. The seam (13 JSON inputs in, `Determination` out) is exactly the one the report identifies as the part worth keeping (`OpenAPS.swift:410-504`, `553-686`).

Decision rule for later: the rebase (S0.5) proceeds in parallel after S0.4 and is adopted only when the differential gate passes; if it never passes, the plan continues on `JSOrefCore` without losing any Stage 1–2 work.

### 0(b) Where the replay harness runs, and how the same code runs everywhere

**Recommendation: one local Swift package, `AlgorithmKit/` (new top-level directory, `Package.swift`, platforms iOS 17 and macOS 14), consumed by the app as a local SPM dependency and tested on macOS with `swift test`.** Contents: `DosingCore` protocol and `JSOrefCore` (JavaScriptCore is available on macOS, so the identical bundle runs), all pure value-type algorithm modules (supervisor, sizing, estimator, learner), the replay engine, metrics, scenario/trace file formats, and a `trio-replay` executable target. No Core Data, Swinject, UIKit or `FileStorage` inside the package; the app's `OpenAPS`/`APSManager` adapt Core Data rows into the package's value types.

Guarantees that device and harness run the same algorithm:

- Single source: the app links the package; there is no copy. `Trio.xcodeproj` gets the package added once (the one `pbxproj` edit of the plan outside the rebase).
- The JS bundle is a package resource (`AlgorithmKit/Sources/JSOrefCore/Resources/bundle/*.js`), and `Trio/Resources/javascript/bundle/` becomes a symlink to it (or the CI job `scripts/check-bundle-parity.sh` fails when the SHA-256s differ). `scripts/webpack.config.js` output is unchanged.
- Every loop trace and every replay report records `algorithmFingerprint = {gitSHA, packageSHA, bundleSHA256s, coreName}`; the comparison report refuses to compare traces with different fingerprints unless told so. `BuildDetails.plist` (filled by `scripts/capture-build-details.sh`) already carries the git SHA for the installed build.
- The JS core's non-determinism is removed in S0.2 (clock injection), and `DosingCore.run(inputs:clock:)` is a pure function of its arguments by contract, enforced by the golden tests.

Python is used only where Swift would be a reimplementation: driving simglucose/the personal twin (0(c)) and notebook analysis over the JSONL reports. Python calls the `trio-replay` CLI as a subprocess, the same way `LoopAlgorithmRunner` takes scenario JSON (OSS note Q3).

### 0(c) In-silico simulator and wiring

**Recommendation: simglucose (UVA/Padova 2008 cohort, 30 virtual subjects, pip-installable) as the screening cohort, plus a ReplayBG-style personal twin fitted to the user's own 90-day export for counterfactual dosing; T1DMSIM optional for a third opinion.** Reasons: simglucose is Python, scriptable per 5-minute step, and has the 2026 counter-regulation/activity extension the report cites; the UVA digital-twin lineage is the only one with an RCT behind its use for parameter re-optimization (report, item 5, 72→77% TIR). ReplayBG itself is MATLAB; use its published model structure through the Python port (PyReplayBG) or, if that is unavailable or unfit, fit a reduced twin (Bergman-type minimal model with a two-compartment subcutaneous insulin model and a two-compartment gut model) by least squares over the user's detected meal episodes. The twin's fit quality must be reported (30-/60-minute RMSE on held-out days; planning figure 15–25 mg/dL at 30 minutes, report Validation plan) before any counterfactual from it is trusted.

Wiring (`tools/insilico/`, Python): a `TrioController` adapter implements the simulator's controller interface; at each 5-minute step it appends the new CGM value and the previous step's enacted insulin to a scenario state, writes a `tick.json` (glucose history, pump history, profile, preferences, custom variables, clock), invokes `trio-replay tick --core js --stages <config>`, reads `decision.json` (`rate`, `duration`, `units`, trace), and applies `rate` as basal and `units` as a bolus. Determinism: fixed seeds for sensor noise and meal schedules; a scenario file lists meals (time, grams, absorption class), exercise bouts, missed doses, sensor dropouts and compression artifacts. Runtime: ~50–100 ms per JS tick → ~30 s per subject-day; the per-PR set (3 subjects × 3 days × 4 scenarios ≈ 20 minutes) runs in CI, the full set (30 subjects × 14 days × 8 scenarios ≈ 7 hours) runs nightly or on demand.

In-silico false-positive rates understate real ones (report, item 6: 0.05/day in silico vs 0.17 on OhioT1DM), so simulation screens for gross failures and gives floors; the user's own data decides promotion.

## 1. Workstreams and ordered steps

Conventions used in every step:

- **Stage modes.** Every new dosing component is a `DosingStage` with a persisted `mode: DosingStageMode` ∈ {`off`, `shadow`, `reduceOnly`, `live`}, default `off`. `shadow` computes and logs but changes nothing; `reduceOnly` applies only reductions of insulin; `live` applies everything. Modes live in a new `AlgorithmLabSettings` struct nested in `TrioSettings` (persisted in `freeaps/freeaps_settings.json`), and a master `algorithmLab.killSwitch: Bool` (default `false`) forces every stage to `off` except the supervisor, which stays in whatever mode it has (it can only subtract). This is the report's "one-tap kill switch that reverts to Stage 1 behaviour and never to the pre-supervisor fork".
- **Hook point.** A new `DosingPipeline` runs inside `OpenAPS.determineBasal` immediately after `determination.timestamp = deliverAt` (`OpenAPS.swift:512`) and before `processDetermination(determination)` (`:538`), so the stored `OrefDetermination` that `APSManager.enactDetermination` reads (`APSManager.swift:1682-1716`) is the post-pipeline decision. Derived per-loop input overrides (the PR #1506 pattern) are applied in the same function where `preferences` is already mutated for dynamic ISF (`OpenAPS.swift:478-482`) and where `profile`/`autosens`/`trioCustomOrefVariables` are assembled.
- **Trace.** Every stage appends a `DosingStageTrace {stage, mode, proposalIn, proposalOut, reasons[], numbers{}}` to the loop's `DosingTrace`, written by `DosingTraceStore` (S0.3). "Telemetry fields" below are keys inside `numbers`.
- **Gates** are evaluated by `trio-replay report` and reported in the format of §2.4. "Non-inferior" means: the upper bound of the 90% block-bootstrap confidence interval of (candidate − baseline) is within the margin.
- **Standard safety margins** (report, Validation plan; numeric margins are this plan's choices): TBR <70 margin +0.3 percentage points, TBR <54 margin +0.1 pp, LBGI margin +0.2, max rolling-60-minute SMB total not above baseline's 99th percentile, IOB never above `max_iob`, detector ≤0.5 FP/day, predicted-low recall ≥95% of actual <70 events with ≥30 minutes of warning in replay, total insulin/day within ±10% of baseline unless the step's purpose is to change it.
- **Shadow duration**: ≥4 weeks and ≥20 detected meal episodes (report, Environment 4) unless stated otherwise; each live sub-step held 2 weeks.
- **Shadow modules referenced**: `AdaptiveKalmanFilter`, `BGSignalProcessor`, `BGResidualCalculator`, `MacroMealModel`, `ExerciseSensitivityModel`, `DailyStateVector`, `GarminZScoreNormalizer`, `AdaptiveLearning`, `SignalStore`, `OrefSignalPipeline` (all `Trio/Sources/APS/SignalProcessing/`), `MealClassifier` (`Trio/Sources/APS/MealClassifier.swift`), `PumpSiteAge` (`Trio/Sources/APS/PumpSiteAge.swift`), `SmartSenseManager` (`Trio/Sources/Services/SmartSense/`).

Effort is in developer-days for one developer; calendar time is longer because shadow periods are wall-clock.

### 2.2 Deterministic replay engine

`ReplayEngine.run(history: HistoryStore, core: DosingCore, pipeline: DosingPipeline, from: Date, to: Date, mode: .faithful | .counterfactual)`.

- **Tick schedule.** One tick per stored loop (`LoopRecord.clock`), not a synthetic 5-minute grid, so cadence quirks (3-minute `Config.loopInterval`, G7 late readings, skipped loops) are reproduced. `.faithful` mode replays every stored loop with its stored inputs byte-for-byte (`verify` subcommand); `.reconstructed` mode rebuilds the inputs from entities for the same tick times (used for the backfilled period and to validate the reconstructor against stored inputs).
- **Reconstruction per tick (`TickReconstructor`).** Glucose: the 72 most recent `GlucoseStored` rows at or before `clock` (as `fetchAndProcessGlucose(fetchLimit: 72)`), smoothed value substituted when `smoothGlucose` was on at that time (from the settings snapshot), manual readings always raw (`OpenAPS.swift:160-170`). Pump history: events in `[clock − 24 h, clock]` with the orphaned-resume filter applied as of `clock`; a bolus being delivered at `clock` is included at its start time as the app does. `currentTemp`: derived from the last temp-basal event minus elapsed minutes (`APSManager.fetchCurrentTempBasal` fallback path, `:1643-1668`); the live path's pump-reported `basalDeliveryState` is not reconstructible, so `verify` tolerates `duration` differences of ≤1 minute and flags larger ones. Carbs: 24 h excluding rescue. Profile: the snapshot in force at `clock` (settings snapshot history, with `profileProvenance`). Autosens: re-run `autosens.js` on the reconstructed inputs when the stored `settings/autosense.json` is older than 30 minutes at `clock`, exactly as `APSManager.autosense()` does. TDD: `TDDStored` row at or before `clock` and the 10-day/2-hour averages as `prepareTrioCustomOrefVariables` computes them. Overrides/temp targets: the run active at `clock`. `monitor/iob.json`: produced by the core's `iob` entry point on the reconstructed history (and compared with the stored one in `TickReconstructorTests`).
- **Counterfactual mode.** When a candidate changes a decision, later inputs in the real history no longer correspond to what the candidate would have produced. Two approximations are used, and the report states which produced each number: (1) **decision-divergence scoring** (default, Environment 3): each tick is scored independently on stored inputs; divergence metrics are computed per tick (Δunits, Δrate, direction of change) and contextualised by what actually happened next (glucose at +30/+60/+120 min, any <70 within 2 h, any >250 within 2 h), yielding "would have dosed more into a later low" and "would have dosed more into a confirmed rise" counts, plus insulin-delivered deltas accumulated per day; the candidate's IOB is propagated through its own decisions so budgets and ceilings are evaluated on candidate IOB, not stored IOB; (2) **twin resimulation** (Environment 2): the personal twin (S0.7) generates counterfactual glucose from the candidate's deliveries, which is the only way to answer "would the sushi meal have ended without a 3 a.m. low"; twin outputs are reported with the twin's fit RMSE and never pooled with divergence scores.
- **Determinism.** Fixed `clock` per tick, fixed fingerprint, fixed seeds; `verify` is the contract.

### 2.3 Metrics (identical implementation in every environment)

TIR 70–180, TITR 70–140, TBR <70 and <54 (percent, event count, mean duration), TAR >180 and >250, mean/SD/CV, LBGI/HBGI (Kovatchev symmetrisation), postprandial peak and 3-hour AUC above 140 after each labelled episode onset, time from onset to return below 180, total daily insulin and automated fraction (SMB + above-basal temp), suspension count and cumulative zero-temp minutes, max rolling-60-minute SMB total, max IOB excursion, detector sensitivity/precision/median delay/FP per day against the reference set, and **time-to-first-adequate-correction**: minutes from labelled onset until cumulative automated insulin since onset ≥ 50% of `(peak − target)/ISF` using the profile ISF at onset (a sizing-independent definition of "the loop has caught up halfway"). Block-bootstrap (weekly blocks, 2,000 resamples) 90% CIs for differences.

### 2.4 Comparison report format

`trio-replay compare --baseline <fingerprint|tag> --candidate <config> --from --to` writes `reports/replay/<date>-<candidate>/`: `summary.json` (every metric for baseline and candidate with CI and gate verdicts `pass|fail|n/a`), `divergence.jsonl` (per-tick rows), `episodes.csv` (per labelled episode: onset, class, detection time, peak, AUC, insulin, min BG after), `daily.csv`, and `report.md` (the gate table first, then metrics, then the ten largest divergences with their context). The gate table lists each promotion-gate criterion from §1 with the number, the margin, and the verdict; a step is promotable only when every row passes.

### 2.5 Reference meal-episode set (no carb log required)

`EpisodeLabeler` labels onsets retrospectively from glucose alone: a rise of ≥35 mg/dL within 60 minutes or velocity ≥1.5 mg/dL/min sustained 15 minutes, starting from a local minimum, with the onset placed at the last tick before velocity exceeded 0.5 mg/dL/min, excluding rises within 30 minutes after rescue carbs, within 60 minutes after a calibration or new sensor, and rises that reverse within 30 minutes (noise). Episodes are merged if onsets are <90 minutes apart; the end is the first return below the onset glucose + 20 or 6 hours. Each episode records time of day, slope, time-to-peak, duration, cumulative residual, and whether a tap/carb entry existed (as metadata only). The 30-episode hand-labelled calibration set (S0.4) fixes the thresholds; thereafter labels are automatic. Split by tap/no-tap and report subject-wise (per the report's validation plan). Labels are computed from *future* glucose and are therefore unavailable to any live component; detectors are scored against them, never trained on them in a way that peeks ahead (training windows end at the onset, the label is the target).

## 3. Safety supervisor specification

The supervisor is unconditionally first because every other change in this plan adds insulin somewhere, and the only mechanism that bounds all of them at once is a layer that runs last, sees the final proposal, and can only subtract. It is the report's item 2, the Boost "floors that can only tighten", the 780G predicted-low subtraction, and zone-MPC's velocity weighting in one module, and it is also what makes the later kill switch safe to use (reverting to "supervisor only" is always safer than baseline). It runs in the pipeline after every other stage and after `killSwitch` evaluation, in the package, with no dependency on which core produced the proposal.

Inputs: `DosingProposal {units, rate, duration}`, `LoopContext {glucose samples (with noise/device/isCalibration/sessionStart), Kalman state (bg, v, a, uncertainties, age), iob, iobArray, maxIOB, basal, maxSafeBasal, TDD, target, threshold, insulin curve/peak, episode state (from S2.1 when present), wearables, site age, clock}`. Output: `DosingProposal` with `units' ≤ units`, `rate' ≤ rate` (a zero temp may be lengthened to 30 minutes), plus a trace.

3.1 **CGM quality gate** (first; replaces the inert JS branch at `determine-basal.js:534-579` for the Swift layers while leaving it in place). `stale` (newest ≥12 min or clock skew < −5 min): `units = 0`, `rate ≤ basal`. `noise ≥ 3` or `bg ≤ 38`: same. `noise == 2`: `units ×0.5`, and the sizing/detector are told `cgmQuality = noisy`. `calibrating`: any `isCalibration` sample in the last 15 minutes → `units = 0`. `newSensor`: `sessionStart` within 2 hours → `units = 0`. Raw-vs-smoothed divergence >20% of bg → `units = 0`. `noise == nil` → `unknown`: no reduction, but the lockout relaxation (S1.4) and detector bonus are disabled; the trace marks it so the proportion of unknown loops is visible (if it stays high for a CGM, the plugin needs a field mapping).

3.2 **30-minute predictive suspend.** `predBG30 = bg + 30 v` using Kalman velocity (fallback: least-squares slope over the last 6 readings when the Kalman state is >7.5 minutes old). If `bg < 70` or `predBG30 < 80`: `units = 0`, `rate = 0`, `duration = max(duration, 30)`. Hysteresis: stay suspended until `predBG30 ≥ 90` and `v ≥ 0` on two consecutive ticks. Maximum continuous zero temp 150 minutes, after which basal resumes at 50% for 30 minutes unless `bg < 70` (then the suspend continues and a carbs-required notification is raised via the existing `carbsReq` path). Daily cap on suspend minutes is not enforced (safety), but `sup.suspendMinutesToday` is tracked for the over-suspension metric.

3.3 **Velocity gate.** `g(v) = 1` for `v ≥ 0`, `0` for `v ≤ −1 mg/dL/min`, linear between; `units ×= g(v)`; above-basal temp: `rate = basal + (rate − basal) × g(v)`. Deceleration brake: if `a < −0.05 mg/dL/min²` and `bg < 180`, `units ×= 0.5`. This is the zone-MPC `Q(v)` idea and the second half of report item 4; it acts regardless of whether S1.4's lift is enabled.

3.4 **IOB ceiling.** SMBs may not push `iob + units` above `iobCeilingPercent × maxIOB` (default 90%, autoISF `iobTHvirtual` lineage with the tolerance folded into the percent); temp basals may fill to 100% (the core already stops at `max_iob`, `determine-basal.js:1687-1691`). With `maxIOB = 0` (the fork's default) nothing doses anyway.

3.5 **Rolling budgets.** Rolling-60-minute automated insulin (SMBs + above-basal temp delivered) ≤ `max(1.0 U, 8% × TDD)`; rolling-180-minute ≤ `15% × TDD`; per detected episode (from S2.1; before that, per 6-hour window) ≤ `20% × TDD`. The defaults are calibrated in S1.1 replay so that <2% of baseline SMB volume on non-window days is clipped; the clip count is a standing dashboard item. Budgets are per-stage reductions on `units` first, then `rate`.

3.6 **Anti-windup exits** (780G-style). Max temp (`rate ≥ maxSafeBasal` or SMB at cap) for 420 continuous minutes → fall back to profile basal and `units = 0` for 60 minutes with a notification; zero temp cumulative ≥ 180 minutes in any 6 hours → the 50%-for-30-minutes rule of 3.2 and a notification. Both are logged as `sup.antiWindupState`.

3.7 **Insulin onset accounting.** For the ceiling and budgets, insulin delivered within the insulin's onset time (`rapid-acting` 20 min, `ultra-rapid` 12 min, or `insulinPeakTime/4` when custom) is counted at 100% even though the IOB curve shows near-zero activity; this is the subtract-only use of insulin-specific timing (report item 2).

3.8 **Hard floor (`supervisorHardFloorEnabled`, default `true`, cannot be turned off by `killSwitch`).** Regardless of all modes: `units = 0` if `bg < threshold` (the core's `threshold` from `determine-basal.js:733-737`, stored on `OrefDetermination.threshold`), and `units ≤ smbAbsoluteCap (3.0 U)`.

Tests are listed in S1.1; the property test `testNeverIncreasesUnitsOrRate` and the trace assertion in shadow are the invariant. Why unconditionally first: items 3, 4, 6, 7, 8 and 5's "may raise insulin" branch each need a bound that is independent of their own logic; the supervisor provides it once, is itself validated against the user's history for predicted-low recall and false-suspend rate, and its failure mode (over-suspension) is measured by the suspension metrics before it goes live.

## 4. Measurement and decision framework

- **Baseline period.** 28 days of recording with the frozen baseline (S0.1) before any live change, plus the backfilled 90 days for replay. Minimum per evaluation arm: 14 days and ≥10 labelled episodes per arm; learner evaluations need ≥28 days per arm.
- **Design.** For reversible, fast-acting changes (supervisor, sizing, lockout/brake, detector, integrator, absorption, wearables): ABAB alternating-week crossover (A = previous state, B = candidate), minimum two full cycles (4 weeks), with the first 24 hours of each switch treated as washout. For stateful slow changes (learner): interrupted time series with a 4-week pre-period, and the learner's own walk-forward replay as the primary evidence. Pre-register for each step, in `docs/experiments/<step>.md` before flipping the toggle: the primary endpoint, the co-primary safety endpoints (TBR <70, TBR <54, LBGI, max 60-min SMB stacking), the margins (§1 standard margins), the arm length, and the analysis (paired day-level differences, weekly block bootstrap, 90% CI).
- **Confounders.** Site changes: exclude the first 6 hours after a pod change from episode metrics and tag the day; stratify by site-age band (0–24, 24–48, 48–72, >72 h) in the dashboard. Illness/stress: a user "sick day" flag (one toggle, logged as a telemetry event) excludes the day from both arms. Travel: time-zone change detected from the device (compare `TimeZone.current` across loops) excludes ±1 day. New sensor: first 12 hours excluded from detector metrics. Exercise: Garmin/HealthKit-detected days are a stratum, never excluded (they are a target of S2.6). Therapy-profile switches and manual settings edits reset the current arm.
- **What counts as a win.** The primary endpoint improves with its 90% CI lower bound above zero (or above the pre-registered minimum: AUC −10%, TAR −3 pp, TIR +3 pp, time-to-first-adequate-correction −10 min), and every safety co-primary is non-inferior at its margin. A step that wins on the primary but breaches a safety margin is an "iterate" (tighten the step's own parameters, re-shadow 2 weeks). A step that neither wins nor loses after two cycles is reverted (the shadow modules precedent: Boost dropped three components this way).
- **Standing dashboard** (`trio-replay dashboard`, nightly from traces; also the `AlgorithmLab` screen in the app): TIR/TITR/TBR<70/TBR<54/TAR>180/TAR>250, mean/SD/CV, LBGI/HBGI (7-day and 28-day, by arm); postprandial peak and 3-h AUC per labelled episode (rolling 20 episodes); time-to-first-adequate-correction; insulin/day and automated fraction; SMB count, max 60-min stacking, IOB max; suspensions count/minutes, false suspends/day, rebound highs after suspend; supervisor clip counts by rule; detector sensitivity/precision/delay/FP per day (live, judged by subsequent glucose) and tap-day vs no-tap-day split; learner per-block values vs corridor and evidence counts; CGM quality distribution (`ok|noisy|unknown|stale`); fingerprint drift (trace fingerprint ≠ expected); loop duration p95.

## 5. Risk register and stop conditions

| Stage | Risk | Type | Mitigation |
|---|---|---|---|
| 0 | Replay not faithful (reconstruction drift, clock, pump-state) | technical | `verify` ≥99.9% gate; tolerate only the documented `currentTemp` duration ±1 min; fingerprint on every record |
| 0 | Rebase breaks fork features or changes decisions silently | technical | S0.5 differential gate ≥99.5%; keep `JSOrefCore` selectable; rebase is not on the critical path |
| 0 | Trace storage fills the device | data | gzip day files, 90-day purge, size test ≤60 KB/loop |
| 1 | Supervisor over-suspends → rebound highs | physiological | false-suspend ≤2/day and suspension minutes ≤ baseline+60 in replay; hysteresis; 150-min cap |
| 1 | Supervisor bug increases insulin | technical | subtract-only property test, shadow trace assertion, hard floor independent of modes |
| 1 | Retiring the meal-window stack raises TAR for weeks | physiological | planned; S1.3/S1.4 follow within the same release train; the user is told the expected TAR cost from replay |
| 1 | Ranged sizing stacks SMBs on slow-absorbing meals | physiological | budgets, IOB ceiling, brake, `reduceOnly` first, `upper 0.6` first |
| 1 | Kalman filter misreads a calibration jump as acceleration | data | `isCalibration` field, 30-min calibration lockout, `unknown` noise disables the lift |
| 2 | Detector false positives dose into a non-meal | physiological | ≤0.5 FP/day gate on the user's own data, FP rollback with zero temp, episode budget, `reduceOnly` first |
| 2 | Integrator "aggressive up front, low on the tail" | physiological | COB>40 suppression, Recovering suppression, 40 mg/dL positive cap, velocity clamp |
| 2 | Learner learns from bad periods (overrides, phantom COB days, illness) | data | exclusion rules; reduce-only first; corridor ±30%; review-before-consume for 4 runs; sick-day flag |
| 2 | Wearable data gaps | data | fail-safe: no data → no action; `wear.dataAgeMin` on the dashboard |
| 3 | Shadow core looks good on replay but not live | technical | ≥3 months shadow, twin, `reduceOnly` first |
| D | Glucagon pharmacology / device compatibility unknown | physiological/legal | D0 written feasibility; proposal-only mode; budgets; the controller must never learn to rely on it |
| all | Solo developer bandwidth; shadow periods overlap with life | process | one live rollout at a time; the checklist in §6; every step independently revertible by one toggle |

**Stop conditions (halt the program, revert to the last promoted state, write an incident note before anything else):**
1. Any glucose <54 mg/dL for ≥15 minutes, or any event needing assistance, within 6 hours of a decision where the candidate delivered more insulin than baseline would have (from the trace).
2. Two nights in any 7 days with a <70 event that the trace attributes to a non-baseline stage.
3. A supervisor trace showing `unitsOut > unitsIn` or `rateOut > rateIn` even once.
4. Fingerprint drift (device running code the replay was not run on) during a live arm.
5. `verify` rate below 99% for 3 consecutive days (the harness no longer describes the device).
6. Detector live FP >1.0/day for 7 days, or any FP that ended below 60 mg/dL.
7. Learner proposing a value outside its corridor, or the same-hour low on 2 nights after a learned change.
8. Rising occlusion/pod-fault rate (>1 per week above the baseline rate) after any change that increases per-SMB size.
9. For the dual-hormone track: any unconfirmed enactment, any budget breach, or any sign that insulin aggression rose because glucagon was available.

Validate
