## Key Question 1: How does autoISF (AAPS) compute its ISF modifiers, what do users report, is it merged into AAPS master, and is there a Trio port?

### Takeaway
autoISF (ga-zelle, now v3.2.1 on top of AAPS 3.4.2.6) replaces oref1's single `sens` with `profile.variable_sens = profile ISF / liftISF`, where `liftISF` is the strongest of four multiplicative factors (acce_ISF from a parabola fit to recent BG, bg_ISF from a piecewise-linear function of BG distance from target, pp_ISF from short-term delta, dura_ISF from time-weighted "stuck high" area), clamped to `autoISF_min..autoISF_max`, plus an IOB-threshold brake and a BG-dependent SMB delivery ratio. It is **not** in nightscout/AndroidAPS master (release notes through 3.4.2.6 never mention it); it lives in the T-o-b-i-a-s/AndroidAPS fork. For Trio, there is **no upstream nightscout/Trio PR**; the port exists as the separately-maintained fork **Tai** (mountrcg/Tai), which has already been re-based onto Trio 1.0's Swift oref.

**Mechanics (verbatim from the Kotlin plugin, branch 3.4.2.6+aisf3.2.1, `plugins/aps/src/main/kotlin/app/aaps/plugins/aps/openAPSAutoISF/OpenAPSAutoISFPlugin.kt`)** — [OpenAPSAutoISFPlugin.kt](https://github.com/T-o-b-i-a-s/AndroidAPS/blob/3.4.2.6+aisf3.2.1/plugins/aps/src/main/kotlin/app/aaps/plugins/aps/openAPSAutoISF/OpenAPSAutoISFPlugin.kt)
- Parabola fit (input to acce_ISF): a quadratic `a0 + a1·t + a2·t²` is fitted to recent glucose (coefficients `glucose_status.a1`, `.a2`, correlation `fit_corr`, computed in `GlucoseStatusCalculatorAutoIsf`, not in this file). Used only when `glucose_status.a2 != 0.0 && fit_corr >= 0.9`; `fit_corr < 0.9` bypasses acce_ISF. Extremum extrapolation: `var minmax_delta: Double = -glucose_status.a1 / 2 / glucose_status.a2 * 5` (minutes to the vertex; `*5` converts 5-min blocks to minutes).
- acce_ISF: `val fit_share = 10 * (fit_corr - 0.9)` (0 at r=0.9, 1 at r=1.0); `acce_ISF = 1.0 + bg_acce * cap_weight * acce_weight * fit_share`, where `acce_weight` is `bgAccel_ISF_weight` (positive acceleration → stronger ISF, i.e. factor >1) or `bgBrake_ISF_weight` (deceleration → factor <1); below target with positive acceleration >1 `cap_weight = 0.5`; above target the sign logic reverses; "braking starts when `minmax_delta <= 30 && minmax_value < target_bg`" (i.e. the parabola's vertex is predicted within 30 min and below target).
- bg_ISF: `val bg_off = target_bg + 10.0 - glucose_status.glucose`; `val bg_ISF = 1 + interpolate(100 - bg_off)`; `interpolate()` is piecewise-linear over `polyX = [50, 60, 80, 90, 100, 110, 150, 180, 200]`, `polyY = [-0.5, -0.5, -0.3, -0.2, 0.0, 0.0, 0.5, 0.7, 0.7]`, extrapolated beyond the ends, then scaled by `higher_ISFrange_weight` (above 100) or `lower_ISFrange_weight` (below). So at BG = target+110 the raw factor is +0.5·weight; at target−40 it is −0.3·weight.
- pp_ISF: bypassed if `bg_off > 0.0` (BG below target+10) or `shortAvgDelta < 0`; else `pp_ISF = 1.0 + max(0.0, bg_delta * pp_ISF_weight)`.
- dura_ISF: bypassed if `dura05 < 10.0` minutes or `avg05 <= target_bg`; else `dura_ISF += dura05Weight * avg05Weight * (avg05 - target_bg)` with `dura05Weight = dura05 / 60` (hours stuck in the ±5% band, `glucose_status.duraISFminutes`) and `avg05Weight = weightISF / target_bg` (`weightISF = dura_ISF_weight`; `avg05 = glucose_status.duraISFaverage`).
- Combination: `liftISF = max(dura_ISF, max(bg_ISF, max(acce_ISF, pp_ISF)))`; if `acce_ISF < 1.0` the result is multiplied by acce_ISF (braking always applies); if `bg_ISF < 1.0`, `liftISF = min(bg_ISF, acce_ISF)` or `bg_ISF * acce_ISF` when acce_ISF > 1.0. `withinISFlimits` clamps to `autoISF_min..autoISF_max`, then multiplies by `sensitivityRatio` (autosens / exercise / activity). Output `return min(720.0, round(sens / final_ISF, 1))` on the bg_ISF<1 path, else `round(sens / final_ISF, 1)`.
- IOB threshold: `val iobTHtolerance = 130.0`; `val iobTHvirtual = iobThresholdPercent * iobTHtolerance / 10000.0 * oapsProfile.max_iob * iobTH_reduction_ratio`; `iobTH_reduction_ratio = profile_percentage / 100.0 * sensitivityRatio` only when `iobThresholdPercent != 100`.
- Dynamic SMB delivery ratio: `new_SMB = lower_SMB + (higher_SMB - lower_SMB) * (bg - target_bg) / smb_delivery_ratio_bg_range`, `higher_bg = target_bg + smb_delivery_ratio_bg_range`; clamped to [min,max]; range 0 → fixed `smb_delivery_ratio`; with `fullLoop` returns `max(fix_SMB, new_SMB)`.
- `autoIsfVersion = "3.2.1"`. Default weights, `autoISF_min/max`, SMB ratio min/max are preferences, not in this file (see Gaps).

**Mechanics in determine-basal (`DetermineBasalAutoISF.kt`, same branch)** — [DetermineBasalAutoISF.kt](https://github.com/T-o-b-i-a-s/AndroidAPS/blob/3.4.2.6+aisf3.2.1/plugins/aps/src/main/kotlin/app/aaps/plugins/aps/openAPSAutoISF/DetermineBasalAutoISF.kt)
- `val sens = if (autoIsfMode) { profile.variable_sens } else { adjusted_sens }`; `naive_eventualBG = if (autoIsfMode) round(bg - (iob_data.iob * sens), 0)`; `bgi = round((-iob_data.activity * sens * 5), 2)`; `csf = sens / profile.carb_ratio` — i.e. the autoISF sens is used everywhere oref1 uses sens (predictions, BGI, CSF, insulinReq), not only for the SMB sizing.
- Non-autoISF path keeps `resistanceMax = min(1.5, profile.autosens_max)  // additional safety limit`.
- SMB sizing: `microBolus = Math.min(insulinReq * smb_ratio, maxBolus)`; then `if (microBolus > iobTHvirtual - iob_data.iob && (loop_wanted_smb == "fullLoop" || loop_wanted_smb == "enforced")) { microBolus = iobTHvirtual - iob_data.iob }` — the IOB threshold is a cap on how far an SMB may push IOB (with 30% tolerance over the nominal threshold), active only in enforced/fullLoop SMB modes.
- Full-loop knobs: `if (loop_wanted_smb == "enforced" || loop_wanted_smb == "fullLoop")` enables SMB regardless of AAPS's own gating; `var maxDeltaPercentage = 0.2 // the AAPS default; if (loop_wanted_smb == "fullLoop") { maxDeltaPercentage = 0.3 }` (relaxes the "SMB disabled when BG jumped >20% in 5 min" guard to 30%).
- Also reads `ActivityMonitorRatio` / `ActivityMonitorStepsActive` preferences (step-based sensitivity).

### Inferences
- autoISF is architecturally a *glucose-shape-driven ISF multiplier* (reactive to current BG, slope, curvature, and dwell time) whereas Trio's dynamic ISF is a *TDD-and-BG-level* multiplier; they address different failure modes (autoISF: slow response to a rise / "stuck high" plateaus / overshoot on a fall; dynISF: day-to-day sensitivity drift and BG-level nonlinearity). They can coexist (AAPS applies `sensitivityRatio` on top of `liftISF`), and Tai does exactly that on Trio.
- Because `variable_sens` feeds `naive_eventualBG`, `bgi`, `csf` and the predictions, autoISF changes *predictions and insulinReq together*, not just SMB sizing; porting only the "SMB ratio by BG" piece would be far smaller and safer than porting the full factor stack.
- A Trio port is technically straightforward: Tai already runs autoISF on Trio's Swift oref ("SwiftOref"), and the only upstream blocker visible is policy (Trio removed autoISF hooks from glucose-get-last; no issue/PR exists), not code.
- The IOB-threshold brake (`iobTHvirtual`) is the mechanism autoISF users rely on to limit SMB stacking in full-closed-loop mode; it is a bounded-IOB cap rather than a prediction-based guard, and is independently portable.

### Gaps
- Exact default values for `bgAccel_ISF_weight`, `bgBrake_ISF_weight`, `pp_ISF_weight`, `dura_ISF_weight`, `lower/higher_ISFrange_weight`, `autoISF_min/max`, `smb_delivery_ratio_min/max`, `smb_delivery_ratio_bg_range`, `smb_max_range_extension`, and the parabola fit window (number of readings / minutes) are in the preferences/`GlucoseStatusCalculatorAutoIsf` files and the Quick Guide PDF, which I could not fetch. The Quick Guide (`autoISF3.2.0_Quick_Guide.pdf`) is the authoritative reference.
- No quantitative outcome data for autoISF users (no Nightscout analyses or surveys found).
- "autoISF merged into AAPS 3.3.x" — **not supported**; release notes through 3.4.2.6 never mention it. If the caller has seen claims to the contrary they likely conflate autoISF with AAPS's own *Dynamic ISF* integration in 3.3.0.0.

## Key Question 2: What are AIMI / Boost / eBoost / Tsunami mechanically, and what is "UAM boost" / "SMB on rise" logic?

### Takeaway
Boost (Tim Street, AAPS fork) is the best-documented of these: it keeps oref1 and replaces only the *micro-bolus sizing decision*, first with an 8-tier rule ladder, now with a 5-state meal hypothesis machine (Idle→Observing→Confirmed→Committed→Recovering) plus two on-device gradient-boosted-tree models (hypo-risk: may only reduce; unannounced-meal probability: the only learned component allowed to add insulin), with per-person derived settings; its author reports ~87% TIR / 0.9% TBR fully closed loop in a small cohort. AIMI, eBoost and Tsunami could not be documented from primary sources (Tsunami is confirmed to exist within the autoISF/T-o-b-i-a-s ecosystem via a "UKF smoothing method, added for Tsunami"; AIMI is described in a 2023 Reddit thread as an ML-incorporating fork).

### Cited Findings
- Boost architecture: "Boost keeps the AndroidAPS engine (basal, dynamic sensitivity, predictions, and all safety gates) and replaces only the decision about the size of the next micro-bolus." Original: "eight tiers, each permitting more aggression, chosen each cycle by rules on glucose, its rate of change, and its acceleration"; the tiers "couldn't separate how hard to push from how much to hold back". Current: a meal hypothesis carried across cycles through "Idle, Observing, Confirmed, Committed, and Recovering"; "Confidence scales the response. Recovering winds down the dosing after a meal peak". Other components: a "composed brake", "absolute time-below-range floors that can only tighten, caps on per-meal insulin and on rolling micro-bolus volume, a heart-rate and step-based sleep detector, step-based insulin withdrawal, and an optional heart-rate module (off by default) that uses Karvonen zones". "Two gradient-boosted tree models run on the phone. One estimates sustained hypo risk and can only reduce a dose. The other estimates the probability of an unannounced meal and is the only learned component allowed to add insulin. Nothing learns or adapts during dosing." "Thirteen components run in shadow mode ... until they are scored and promoted or dropped." Settings are "derived per person from their own history and re-derived periodically". — [diabettech: Beyond Carb Counting — Boost's Evolution](https://www.diabettech.com/beyond-carb-counting-boosts-evolution-and-the-limits-of-fully-closed-loop/) **[community, author's own cohort]**
- Boost outcomes: original n=1 four-month run "81.2% time in range (TIR), 5.6% time below range (TBR)"; current group fully closed loop with no meal announcement "about 87% TIR (±6%), TBR averaging 0.9% with a median of 0.7%", "about a quarter of users are above 1% TBR". Accelerating-meal detector "fires on 8.8% of cycles. 40.6% of those are followed by a rise of at least 1.7 mmol/L within 45 minutes, against a 19.6% background rate (154,000 cycles, 11 people)". Hypo-risk "fall model": AUC-type score "0.780 vs 0.746 for glucose plus time of day, on 16 people who contributed no training data"; refit "0.861 vs 0.847 overall". Physiological forecaster "beats 'no change' by about 0.06 mmol/L on average ... retired because a four-column regression on existing data matched or beat it". Failed components: "a rise-outcome estimator (0.730 vs 0.785 for current glucose alone), an anticipatory backout, and a plateau detector that flagged highs already resolving". "Scaling training data stopped helping at roughly 112 people". — same source **[community]**
- Boost author's limits of FCL: "Insulin's slow onset means a conservative loop always lags meals, and no software fully recovers that time"; "Exercise near meals is a major failure point. The planned fix is a user declaration rather than automatic detection"; approach "is probably near the top of what the oref algorithm can achieve without additional therapies, consistent diet or regime"; "Right now in the insulin only world, it still needs some help." — same source
- Boost-master-v3 is published as an AAPS fork repository. — [tim2000s/Boost-master-v3](https://github.com/tim2000s/Boost-master-v3)
- Earlier Boost-lineage ISF work ("Dynamic ISF" precursor): Tim Street with Chris Wilson (Glucose Genius) added a TDD- and weight-based ISF model to oref1 in AAPS; 7-day-average TDD alone "didn't detect variations in sensitivity and insulin use"; revised to blend "real-time delivered insulin, extrapolated over the rest of the day, with the 7-day history" as a weighted average; using oref1's *eventual* predicted glucose for the ISF "could produce over-large boluses while glucose was rising", so the later model "uses the future value when glucose is flat or falling and the predicted value is lower, and blends current and future glucose when glucose is rising"; used ~4 months in a fully closed-loop setup, "a stable model". — [diabettech: Automating ISF in open source AID systems](https://www.diabettech.com/automating-isf-in-open-source-aid-systems-experiments-with-androidaps/) **[community n=1–2]**
- Tsunami: the autoISF repo says "A UKF smoothing method, added for Tsunami" (i.e. Tsunami is a sibling project in the T-o-b-i-a-s/ga-zelle ecosystem); a Feb-2023 r/AndroidAPS thread describes Tsunami as "a very interesting approach to full closed loop" that "does rely on having a reliable CGM and fast acting insulin, ideally Lyumjev", and says AIMI "incorporates a ML model, unlike the rule-based forks" (with a licensing complaint about the AIMI maintainer — one user's opinion). — [ga-zelle/autoISF](https://github.com/ga-zelle/autoISF); [r/AndroidAPS (redlib mirror)](https://axebps-redlib.hf.space/r/AndroidAPS) **[anecdote]**
- B30 (from the autoISF/Tai feature set, often associated with AIMI-lineage forks): "B30 enables an increased basal rate after an EatingSoon TT and a manual bolus". — [mountrcg/Tai](https://github.com/mountrcg/Tai)
- Baseline oref1 "SMB on rise"/UAM logic (what Boost-type forks modify): AAPS docs — UAM "can recognize fast glucose increases without carb entry and try to correct them with SMBs, and it can stop SMBs early when glucose falls quickly"; SMB pairs micro-boluses with "the actual basal rate is set to 0 IU/h for a certain period to prevent overdose ('zero-temping')"; hard maxIOB caps "3 for children, 12 for adults and 25 for insulin-resistant adults". — [AAPS OpenAPS features](https://androidaps.readthedocs.io/en/3.1/Usage/Open-APS-features.html)

### Inferences
- "UAM boost"/"SMB on rise" in Boost-style forks = raising `smb_ratio`, `maxUAMSMBBasalMinutes` (the per-SMB cap), and relaxing `maxDelta_bg_threshold` conditionally on detected acceleration; autoISF's `fullLoop` mode does exactly the last two (`maxDeltaPercentage 0.3`, `max(fix_SMB, new_SMB)`), so the two lineages converge on the same levers.
- The Boost state machine's key design lesson for Trio is separating *meal confidence* (detection) from *restraint* (brake/caps), and winding down ("Recovering") after the peak to avoid late-stacking lows — the classic oref1 post-meal low.
- Boost's shadow-mode promotion process and per-person derived settings are process innovations that are portable regardless of the specific detector.

### Gaps
- No primary documentation found for AIMI (repo, author, mechanics) or eBoost; "Tsunami" mechanics (reported to use insulin-activity/"wave" timing) could not be verified from any primary source. These should be treated as unverified community names.
- Boost's tier thresholds, state-machine transition rules, model features and caps are not published in the blog; the Boost-master-v3 repo README was not fetched.

## Key Question 3: Loop's algorithm — how does it differ from oref (RC, IRC, momentum, ICE, 30-min temp, auto-bolus fraction), and pros/cons vs oref?

### Takeaway
Loop predicts `BG[t] = Insulin[t] + Carb[t] + RetrospectiveCorrection[t] + Momentum[t]` with dynamic carb absorption (ICE) and a 30-min retrospective-correction velocity decayed over 60 min; the optional Integral Retrospective Correction (IRC, "Algorithm Experiments") is a PID-like accumulator over a 180-min discrepancy window (`persistentDiscrepancyGain 2.0`, time constant 60 min, max effect 180 min, velocity clamp 4 mg/dL/min) and is now in the `LoopKit/LoopAlgorithm` Swift package. Dosing is `dose = (BG_eventual − BG_target)/ISF`, delivered either as a 30-min temp basal (`BR_correction = 2 × dose/hr`) or as an automatic bolus of 40% of the recommendation (20–80% glucose-based in an experiment), with zero-temp whenever min predicted BG < suspend threshold. The only controlled head-to-head vs oref1 is an animal study (pigs, no meal announcement): AndroidAPS TIR 58±5% vs Loop 35±5%.

### Cited Findings
- Overall model: "BG[t] = Insulin[t] + Carb[t] + RetrospectiveCorrection[t] + Momentum[t]"; insulin "exponential model with insulin activity duration of 6 hours", peaks "around one hour"; per-dose effect `ΔBG_dose[t] = ISF[t_dose] × IA_dose[t]`; scheduled basal is baseline, only temp deviations count; IOB can be negative. — [LoopDocs: Glucose Prediction](https://loopkit.github.io/loopdocs/operation/algorithm/prediction/)
- Carbs: 10-minute no-absorption delay; `MAR[t] = CA[t] / (1.5 × d)` (minimum absorption rate, duration effectively extended 50%); dynamic absorption via insulin counteraction effect `ICE[t] = ΔBG_O[t] − ΔBG_I[t]`, converted `AC[t] = ICE[t] × CIR / ISF`, split across meals in proportion to MAR; floor at the minimum rate "to ensure that meal entries expire in a reasonable amount of time"; remaining carbs `ΔBG_C[t] = MAR[t] × ISF / CIR`; non-linear absorption model since Loop 2.0. — same source
- Retrospective correction: "A retrospective prediction starts 30 minutes in the past and ends at the current time"; `BG_vel = (1/6) × (BG[0] − RF[0])` mg/dL per 5 min; `ΔBG_RC[t] = BG_vel × (1 − (t−5)/55)` from 5 to 60 min. — same source
- Momentum: linear-regression slope over the last 3 readings (~15 min); `ΔBG_M[t] = M_slope × (1 − (t−5)/15)` (100% at 5 min, 0 at 20 min); blend `ΔBG[t] = ΔBG_M[t] + (ΔBG_I + ΔBG_C + ΔBG_RC) × min((t−5)/15, 1)`; not computed if CGM data non-continuous or any of last three is a calibration. — same source
- IRC (enabled under "Algorithm Experiments", "replaces the Retrospective Correction (RC)"); chart shows "Integral effect" as "the difference between the IRC and RC calculations". — same source
- IRC constants (verbatim): `retrospectionInterval = 180 min`; `currentDiscrepancyGain = 1.0`; `persistentDiscrepancyGain = 2.0 // was 5.0`; `correctionTimeConstant = 60 min // was 90.0`; `differentialGain = 2.0`; `delta = 5 min`; `maximumCorrectionEffectDuration = 180 min // was 240.0`; `integralForget = exp(-delta/correctionTimeConstant)`; `integralGain = ((1 - integralForget)/integralForget) * (persistentDiscrepancyGain - currentDiscrepancyGain)`; `proportionalGain = currentDiscrepancyGain - integralGain`; `defaultMaxCorrectionVelocity = 4.0/60 mg/dL/s` ("top of physiologically-plausible sustained unmodeled glucose velocity (~4 mg/dL/min)"). Algorithm: keep only a contiguous run of same-sign discrepancies (≥0.1 mg/dL) walking back from the newest; `integral = integralForget × integral + integralGain × discrepancy` recomputed from zero each call (sign change = reset); effect duration = `effectDuration − 10 min + 10 min per discrepancy`, cap 180 min; differential term `differentialGain × (current − previous)` only when negative ("to avoid upward momentum stacking"); total = P + I + D, scaled `× effectDuration / integralDuration`, divided by max(span, 30-min grouping interval), clamped to ±max velocity, applied via `decayEffect`. — [IntegralRetrospectiveCorrection.swift (LoopKit/LoopAlgorithm)](https://github.com/LoopKit/LoopAlgorithm/blob/main/Sources/LoopAlgorithm/RetrospectiveCorrection/IntegralRetrospectiveCorrection.swift)
- IRC history: PR #726 (ps2, May 2018) added an on/off switch and RC breakdown; reviewer safety concern: with overestimated carbs absorbing faster than expected "integral RC would initially accumulate positive discrepancy leading to more aggressive dosing up front and more likely low on the tail end" → proposed reset when discrepancy positive and carb effect > `carbEffectLimit`; states recomputed from the past 60 min on restart. — [LoopKit/Loop PR #726](https://github.com/LoopKit/Loop/pull/726)
- Dosing: `dose = (BG_eventual − BG_target) / ISF`; `BR_correction = 2 × dose / hr`; `BR_required = BR_scheduled + BR_correction`; `BR_temp = max(min(BR_required, BR_max), 0)`; "All temporary basal rate commands are issued for a duration of 30 minutes" (may be reissued every 5 min; not reissued if ≥10 min remain); Automatic Bolus: "an automatic bolus, which is less than the recommended dose, is delivered promptly" — default "40% of the recommended bolus, and with the Glucose Based Partial Application experiment it ranges from 20% to 80%, depending on glucose"; "If the minimum predicted glucose goes below the suspend threshold, then Loop will issue a temporary basal rate of zero"; no automatic increase while BG is below the correction range. — [LoopDocs: Automatic Dosing Adjustments](https://loopkit.github.io/loopdocs/operation/algorithm/auto-adjust/); [LoopDocs: Algorithm overview](https://loopkit.github.io/loopdocs/operation/algorithm/overview/)
- LoopAlgorithm package: "a public Swift Package implementation of the Loop Algorithm" that "forecasts blood glucose from insulin, carbohydrate, and historical glucose inputs, and produces dosing suggestions"; "highly experimental", "not approved for therapy"; includes a `LoopAlgorithmRunner` CLI that takes a scenario JSON; 79 commits on main, no releases listed. — [LoopKit/LoopAlgorithm](https://github.com/LoopKit/LoopAlgorithm)
- Head-to-head evidence: Lal et al. 2021 (Clin Transl Med) compared AndroidAPS and Loop in pigs without meal announcements: "Overall time-in-range (70–180 mg/dl) for AndroidAPS was 58% ± 5%, while time-in-range for Loop was 35% ± 5%"; authors suggest "the oref1 strategies in AndroidAPS may result in a better overall control for full closed loop systems". — [DOAJ record, Clin Transl Med 2021](https://doaj.org/article/b08f806168ca4c878812280d3471a23a) **[animal study]**
- Loop real-world self-report: a BC Diabetes manuscript cites a self-reported Loop study of 558 users, TIR 67%→73%, HbA1c 6.8%→6.5%. — [BC Diabetes Loop study PDF](https://www.bcdiabetes.ca/wp-content/uploads/bcdpdfs/Loop-study-at-BCDiabetessubmitted-to-Lancet-Diabetes-2023-Jan-23.pdf) **[observational, self-report]**

### Inferences
- Structural differences vs oref1: (a) Loop uses a single blended prediction with *continuous* carb absorption inferred from ICE, whereas oref1 runs four separate prediction curves (IOB, COB, UAM, ZT) and doses on the *minimum* of them; (b) Loop's RC/IRC is an explicit model-error feedback term that oref1 lacks (oref1's analogue is the deviation/`uci` term feeding UAMpredBG, plus autosens over 8–24 h); (c) Loop has no SMB-style zero-temp pairing — auto-bolus delivers a fraction and leaves scheduled basal running, so it stacks less but corrects rises more slowly; (d) Loop has no "unannounced meal" curve, which is the most plausible driver of the pig-study gap.
- The IRC's discrepancy-run accumulator with velocity clamp and sign-reset is a compact, well-specified mechanism that could be ported into oref1's deviation handling to make UAM/`predDev` persist in a principled, bounded way instead of oref1's fixed 5-min deviation extrapolation.
- Loop's "Glucose Based Partial Application" (20–80% by BG) is the same idea as autoISF's BG-ranged SMB delivery ratio — two independent lineages converging on "deliver a larger fraction of insulinReq when higher above target".

### Gaps
- Exact Glucose Based Partial Application breakpoints and the `effectDuration`/`recencyInterval` defaults were not captured.
- No peer-reviewed human comparison of Loop vs oref1; Tidepool Loop, Loop Caregiver and the FreeAPS/FreeAPS X→iAPS lineage were not researched in this pass beyond noting that iAPS/Trio descend from FreeAPS X (the local trio-oref history references "iAPS v3.0.3" and "Open-iAPS" renames).

## Key Question 5: Published outcome data for DIY AID, and fully-closed-loop (FCL) experiments by DIY users

### Takeaway
The only RCT is CREATE (NEJM 2022; AndroidAPS 2.8 / OpenAPS 0.7.0, n=97): TIR 61.2%→71.2% with AID vs 57.7%→54.5% control, adjusted difference 14 points (95% CI 9.2–18.8), no severe hypo or DKA. Observational/self-report data (OPEN/DIWHY survey, OpenAPS 2016 poster, Austrian registry) consistently show TIR ~77–84% and HbA1c ~6.2–6.5%. ## Key Question 6: Community-known weaknesses of oref1 as implemented in Trio/AAPS

### Takeaway
Documented weaknesses cluster into: (1) lag on unannounced meals and higher post-meal peaks because SMB cannot pre-bolus; (2) SMB/zero-temp pairing that produces alternating delivery and a sub-30-min zero-temp emulation bug in Trio's Swift port; (3) dependence on correct ISF/CR/basal, with autosens bounded to ±20–30% (Trio defaults 0.7–1.2; AAPS hard-caps resistance at 1.5) and reduced effectiveness during continuous carbs; (4) dynamic ISF caps (150%) that fail at high TDD and formula drift from AAPS; (5) ISF models driven by eventual BG that over-bolus during rises; (6) no memory of time-of-day patterns; (7) exercise near meals as a hard failure mode.

### Cited Findings
- Post-meal peaks without pre-bolus: "it may be sufficient for meals containing only 'slow' carbs to inform the system of the planned amount of carbohydrate and leave the rest to AAPS. However, this may lead to higher postprandial (post-meal) peaks because pre-bolusing isn't possible"; mitigation "a start bolus, which only partly covers the carbohydrates (e.g. 2/3 of the estimated amount)". — [AAPS OpenAPS features](https://androidaps.readthedocs.io/en/3.1/Usage/Open-APS-features.html)
- Zero-temping by design: "At the same time (for safety reasons) the actual basal rate is set to 0 IU/h for a certain period to prevent overdose ('zero-temping')" — the structural source of the SMB/zero-temp "sawtooth". — same source
- Autosens and carbs: "if continuously eating carbs over an extended period, autosens will be less effective during that period as carbs are excluded from BG delta calculations". — same source
- Autosens bounds: Trio defaults `autosens_max: 1.2`, `autosens_min: 0.7`, clamped in `autosens.js:406-407`; AAPS autoISF code keeps `resistanceMax = min(1.5, profile.autosens_max) // additional safety limit`. — local `/home/user/Trio/trio-oref/lib/profile/index.js`, [DetermineBasalAutoISF.kt](https://github.com/T-o-b-i-a-s/AndroidAPS/blob/3.4.2.6+aisf3.2.1/plugins/aps/src/main/kotlin/app/aaps/plugins/aps/openAPSAutoISF/DetermineBasalAutoISF.kt) **[code]**
- Trio dynISF cap at high TDD: 150% limit "unlikely to work well for anyone with a TDD of > 75u/day"; AAPS allows 300%; Trio formula "differs from AAPS and from the original design intent". — [Trio issue #1075](https://github.com/nightscout/Trio/issues/1075)
- Trio sigmoid caution: TrioDocs "advises against setting Autosens Max above 150% with Sigmoid" and warns raising Autosens Max with sigmoid makes "the speed and amount of ISF changes getting greater". — [TrioDocs Dynamic Settings](https://triodocs.org/configuration/settings/algorithm/dynamic-settings/)
- Swift-port zero-temp bug: "SMB low-temp rate formula is inverted for sub-30m zero temps". — [Trio issue #1359](https://github.com/nightscout/Trio/issues/1359)
- dynISF silently disabled by CGM cadence ("Insufficient TDD for dynamic formula; disabling for determine basal run" on every run). — [Trio issue #1610](https://github.com/nightscout/Trio/issues/1610)
- No time-of-day memory; global aggression knobs are "blunt" and raise hypo risk at other times; user data 76% TIR / 23% >180 with recurring afternoon and overnight highs. — [Trio issue #1516](https://github.com/nightscout/Trio/issues/1516) **[n=1 user data]**
- Eventual-BG-driven ISF over-boluses on a rise: an early dynamic-ISF model using oref1's eventual predicted glucose "could produce over-large boluses while glucose was rising". — [diabettech: Automating ISF](https://www.diabettech.com/automating-isf-in-open-source-aid-systems-experiments-with-androidaps/) **[n=1]**
- Meal lag is intrinsic: "a conservative loop always lags meals, and no software fully recovers that time"; original tier-ladder FCL had "post-meal highs and wider glucose lines than hybrid loops"; "Exercise near meals is a major failure point"; a plateau detector "flagged highs already resolving" and was dropped. — [diabettech: Boost's Evolution](https://www.diabettech.com/beyond-carb-counting-boosts-evolution-and-the-limits-of-fully-closed-loop/)
- UAM-only trade-off: Lyumjev UAM mode cut lows 88% but raised mean glucose/HbA1c relative to hybrid (20% vs 13% time >140). — [diabettech Lyumjev case study](https://www.diabettech.com/lyumjev-a-fully-closed-loop-case-study-with-oref1/) **[n=1]**
- Persistent-error feedback risk (applies equally to any Trio deviation-integration): with overestimated carbs absorbing fast, an integral term "would initially accumulate positive discrepancy leading to more aggressive dosing up front and more likely low on the tail end". — [Loop PR #726](https://github.com/LoopKit/Loop/pull/726)
- Autotune mis-categorises UAM as basal by default, which "can inflate basal recommendations". — [AAPS Autotune docs](https://androidaps.readthedocs.io/en/latest/AdvancedOptions/Autotune.html)
- SMB disabled on fast change: `maxDelta_bg_threshold: 0.2 // maximum change in bg to use SMB, above that will disable SMB` — i.e. oref1 withholds SMBs precisely during the steepest rises; autoISF's fullLoop relaxes this to 0.3. — local `/home/user/Trio/trio-oref/lib/profile/index.js:57`; [DetermineBasalAutoISF.kt](https://github.com/T-o-b-i-a-s/AndroidAPS/blob/3.4.2.6+aisf3.2.1/plugins/aps/src/main/kotlin/app/aaps/plugins/aps/openAPSAutoISF/DetermineBasalAutoISF.kt) **[code]**
- Trio's `insulinReq` uses `min(minPredBG, eventualBG)` and SMB = half of that by default (`smb_delivery_ratio` 0.5, `maxSMBBasalMinutes` 30) — so a low *minPredBG* from any one of the four curves (notably ZT/UAM) zeroes SMBs even when eventualBG is high; this is the mechanism behind "low prediction → zero temp → rebound high" complaints. — local `determine-basal.js:1612,1811` **[code; the complaint itself is community lore I could not source]**

### Inferences
- Several named complaints in the brief ("overshooting SMBs after rises", "stacking", "sawtooth", "COB decay misestimates", "dynamic ISF instability at high TDD") are only partially sourceable: the high-TDD dynISF problem and the zero-temp/SMB structure are documented (issues #1075, #1359, AAPS docs); "sawtooth" and "COB decay" are visible in the code design (zero-temp pairing; `min_5m_carbimpact` floor) but no written community analysis was found.
- The field's convergent fixes map cleanly onto these weaknesses: autoISF acce/pp factors and Boost's state machine → meal lag and the 20% delta SMB lockout; autoISF iobTH and Boost's rolling caps/"Recovering" → stacking; Loop IRC / Boost learned priors / #1516 → persistent-error and time-of-day memory; BG-ranged SMB ratio (autoISF, Loop GBPA) → the fixed 50% delivery ratio.

### Gaps
- No Discord/Facebook/Reddit threads could be cited (Reddit blocks the crawler; Discord is not indexed), so most "community-known" weaknesses rest on docs, GitHub issues and two bloggers (Tim Street, the AAPS Lyumjev n=1 author).
- No quantitative Nightscout analysis of SMB overshoot, sawtooth frequency, or COB-decay error was found.

## Key Question 7 (synthesis): Which innovations could be ported to Trio, and at what cost/risk?

### Takeaway
Ranked by evidence × portability: (1) BG-ranged SMB delivery ratio (autoISF/Loop-GBPA; tiny change at `determine-basal.js:1811`); (2) IOB-threshold SMB cap (autoISF `iobTHvirtual`; one guard); (3) dynISF ceiling/TDD-blend fix already acknowledged in #1075; (4) full autoISF factor stack (proven on Trio in Tai; larger surface, no outcome data); (5) IRC-style bounded discrepancy integrator feeding UAM deviation (well-specified in LoopAlgorithm; needs simulation); (6) Boost-style meal state machine with caps and wind-down (best FCL outcomes but unpublished rules); (7) learned time-of-day priors (#1516; closed "not planned" upstream, so fork-only).

### Cited Findings
- Tai proves autoISF runs on Trio's Swift oref with the full settings surface including overrides. — [mountrcg/Tai](https://github.com/mountrcg/Tai)
- Trio maintainers intend to revisit the log dynISF formula after the Swift port. — [Trio issue #1075](https://github.com/nightscout/Trio/issues/1075)
- Dosing Modes show the accepted upstream pattern for algorithm variants: "derived overrides at two OpenAPS call sites" without touching stored preferences. — [Trio PR #1506](https://github.com/nightscout/Trio/pull/1506)
- IRC is fully specified with constants and bounded by a 4 mg/dL/min velocity clamp and 180-min effect cap. — [IntegralRetrospectiveCorrection.swift](https://github.com/LoopKit/LoopAlgorithm/blob/main/Sources/LoopAlgorithm/RetrospectiveCorrection/IntegralRetrospectiveCorrection.swift)
- Boost's learned components are constrained so that the hypo model "can only reduce a dose" and the meal model "is the only learned component allowed to add insulin", with "absolute time-below-range floors that can only tighten". — [diabettech: Boost's Evolution](https://www.diabettech.com/beyond-carb-counting-boosts-evolution-and-the-limits-of-fully-closed-loop/)

### Inferences
- The lowest-risk high-value changes are those already independently converged on by two lineages (BG-ranged SMB ratio; relaxed SMB delta lockout gated on acceleration; IOB cap). They need no new predictions, only new gating/sizing, and can be shipped behind a Dosing-Mode-style derived override.
- Anything that alters `sens` globally (autoISF factors, dynISF reform) changes all four prediction curves and `insulinReq` simultaneously; it should be validated with a replay harness (LoopAlgorithm-style scenario runner or GlucoBench-style datasets) before live use, as the Trio project has no outcome data for autoISF.
- Boost's governance ideas (shadow mode, monotonic-safety learned components, per-person derived settings) are more portable than its specific detector and would de-risk any Trio ML experiment.

### Gaps
- No simulation framework exists in Trio for A/B-ing algorithm variants; none of the cited DIY innovations publishes replay data.
